# RAG 评测踩坑全录

> 从「qwen3:8b 够不够当评委」到「rerank 接入」的完整复盘
> 按「认知 → 环境 → 数据 → 模型 → 指标 → 工程」六层组织
> 每条都写清：**现象 / 根因 / 解法 / 为什么这么取舍**

---

# 第一部分：认知层（最贵的坑，都在起步阶段）

这几条不是报错，是**方向性误判**。它们不报错，只会让你白走很多路。

---

## 坑 1：以为 Open WebUI 能支撑评测

**现象**：想在 Open WebUI 里上传文件建库 → 提问 → 复制输出 → 跑 Ragas。

**根因**：Ragas 的四个核心指标里，`faithfulness`、`context_recall`、`context_precision` **全部依赖 `retrieved_contexts`（检索到的原文片段）**。而 Open WebUI 界面上只给你**文件名**，点开引用也常常只有标题没有正文。

**解法**：自建向量库（LangChain + numpy/Chroma），脚本直接把 chunk 当变量存下来。

**取舍逻辑**：
- 不是 Open WebUI 不好，它擅长的是**聊天体验和盲测选模型**
- 但「可观测、可导出、参数可编程」这三件事它做不了
- 所以最终架构是**两套并存**：Open WebUI 做人工体验，自建管线做评测，共用同一个 Ollama

> **一句话**：评测量的是「检索到了什么原文」，拿不到原文就什么都测不了。

---

## 坑 2：以为手工整理数据集能撑到调参阶段

**现象**：设计流程「提问 → 复制回答 → 粘贴进 CSV → 跑 Ragas」。

**根因**：调参需要**反复重跑**。手工抄 10 条，调一次参数就要重抄一轮，调五次就放弃了。而评测的全部价值恰恰在于反复对比。

**解法**：脚本化。`run_batch.py` 自动跑完所有问题，自动存 xlsx。

**取舍逻辑**：
- 手工适合**第一次验证流程跑通**（10 条，半小时）
- 一旦进入调参循环，必须自动化——否则迭代成本会直接掐死闭环

> **一句话**：评测的价值不在分数，在于「改了参数分数变没变」。手工做不了这件事。

---

## 坑 3：一开始就想把所有指标跑齐

**现象**：直接要四大指标。

**根因**：`context_recall` / `context_precision` 需要 `reference`（标准答案），而标准答案是最大的工作量来源，且质量直接决定指标可信度。

**解法**：分两步。先只跑 `faithfulness + answer_relevancy`（不需要 reference）把链路跑通，再补 reference 上检索指标。

**取舍逻辑**：先跑通再跑全。链路没通就堆指标，会让排错变得不可能——你分不清是数据问题、模型问题还是指标问题。

# 第二部分：环境层（全是报错，但都是一次性的）

---

## 坑 4：`No module named 'langchain_community.chat_models.vertexai'`

| | |
|---|---|
| **现象** | 一 `import ragas` 就炸 |
| **根因** | ragas 0.4.x 硬编码引用了这个模块，但 langchain-community 0.4 已删除它（Google VertexAI 移到独立包）。**官方至今没合并修复 PR** |
| **解法** | 整条 langchain 线锁回 0.3：`pip install "ragas==0.4.3" "langchain-community==0.3.31" "langchain-core<0.4" "langchain<0.4"` |
| **兜底** | 脚本顶部注入 shim 假模块（能正常 import 就不注入，安全） |

**为什么必须整条线一起降**：langchain-community 0.3.31 和 langchain 1.x 不能共存。只降一个会装出依赖冲突。

---

## 坑 5：`UnicodeDecodeError: 0x90 in position 11`

| | |
|---|---|
| **现象** | `pd.read_csv` 读中文 CSV 崩 |
| **根因** | **把 `.xlsx` 直接改后缀成 `.csv`**——文件内容其实还是 xlsx（ZIP 二进制），用任何文本编码去解都必然失败 |
| **解法** | 后缀改回 `.xlsx`，用 `pd.read_excel()`（需 `openpyxl`） |

**为什么改后缀这个动作会骗人**：Windows 默认隐藏扩展名，你以为改成了 csv，实际文件系统里是 `eval_set.csv` 但内容是 xlsx。

**顺带的收益**：换成 xlsx 后，编码、分隔符、BOM **三个坑同时消失**。中文逗号、单元格内换行、引号转义全都不用操心。

> **铁律**：永远不要用 Excel「另存为 CSV」。要么存 xlsx，要么用 pandas `to_csv(encoding="utf-8-sig")` 生成。

---

## 坑 6：`ParserError: Expected 1 fields in line 4, saw 2`

| | |
|---|---|
| **现象** | 表头被当成 1 列，数据行有 2 列 |
| **根因** | Excel 按系统区域设置用了**分号或制表符**分隔，不是逗号 |
| **解法** | 同上，改用 xlsx |

**教训**：我第一版修复只捕获了 `UnicodeDecodeError`，没捕 `ParserError`，导致修复不完整。**教训是——写容错代码时要把同类异常全部列上**（解码错 + 解析错 + 空文件）。

---

## 坑 7：import 是灰色的 / `NameError: Path not defined`

| | |
|---|---|
| **现象** | PyCharm 里 import 显示灰色，运行时报变量未定义 |
| **根因** | 新代码插在文件顶部，而 `import` 写在下面。Python 从上往下执行，调用时它们还不存在 |
| **解法** | **所有 import 必须放文件最顶部**；不要留重复代码（文件里有两段 `pd.read_csv`，第二段覆盖了第一段的修复结果） |

**灰色 import 的含义**：PyCharm 提示"这个没用到"，是代码异味信号，不是报错。

---

## 坑 8：装 chromadb 极慢

| | |
|---|---|
| **现象** | `pip install chromadb` 卡住十几分钟 |
| **根因** | chromadb 会连带拉 onnxruntime、tokenizers、fastapi 等几百 MB 依赖——**慢的元凶就是它**，而且很可能把刚修好的 ragas 环境又搞崩 |
| **解法** | **不用 chromadb**。改成 numpy 暴力余弦检索 |

**取舍逻辑**：知识库撑死几千块，暴力检索毫秒级。为了几千块数据引入一个重型向量数据库，是典型的**用大炮打蚊子**。依赖只剩 `requests numpy pandas openpyxl`，全是小包，秒装。

# 第三部分：数据层（最隐蔽，症状都伪装成"模型不行"）

---

## 坑 9：回答全是 15 字、相似度 0.3

| | |
|---|---|
| **现象** | 10 个问题全是拒答，相似度 0.3 左右 |
| **根因** | `docs/` 里没放真实文档，向量库里只有 1 块占位文字（"把你的原始文档放这里"）。**"召回 1 段"这个数字直接暴露了**——库里总共就 1 块 |
| **解法** | 放真实文档 → 装格式包 → 重建库 → 块数从 1 变成 190 |

**关键诊断技巧**：看「召回段数」比看「相似度数值」更快定位。10 个问题全都召回 1 段 = 库里只有 1 块，不是检索算法问题。

---

## 坑 10：PDF / DOCX / PPTX / HTML 读不到

| | |
|---|---|
| **现象** | 文档放进去了，但块数是 0 |
| **根因** | 解析包没装，脚本**静默跳过** |
| **解法** | `pip install pypdf python-docx python-pptx`（HTML 用标准库解析，不用装包） |

**静默跳过是最坏的设计**。新版加了两个防呆：
- 不支持的后缀**明确列出来**（"有 2 个文件被跳过"）
- 提取到 0 字的文件**单独警告**（扫描版 PDF 用 pypdf 提取出来就是空的）

> 扫描版 PDF（图片拍的）提取出来必然是空——这类文件你会以为进去了，其实库里什么都没有。

---

## 坑 11：PPT 表格噪音污染知识库

**现象**：检索结果里混进 `6月 | | | | 7月 | | | |` 这种空表格行、`[第28页] 全面预算 28` 这种空页。

**根因**：PPTX 提取时表格和空页被切成 chunk 存进库，靠通用词匹配混进 top5，把真正相关的内容挤掉。

**解法**：
- 快：过滤"空表格行占比过高"的 chunk
- 稳：从源文件删掉纯表格页，重建库

**为什么这个问题重要**：它同时压低 precision（噪音占位）和 recall（挤掉正主）。

---

## 坑 12：`reference` 列为空 → 检索指标全跑不了

| | |
|---|---|
| **现象** | 只能跑两个指标 |
| **根因** | `context_recall` / `context_precision` 需要标准答案做尺子 |
| **解法** | `make_reference.py` 半自动生成：让**另一个更大的模型**读「问题+原文」起草，人工确认 |

**为什么可以用模型起草**：起草模型 ≠ 生成模型（14b/31b vs 8b），不是自我循环。

**为什么必须人工确认**：模型会写错、写漏、把无关内容写进去。尤其是**"文档里没有答案"的题**，模型经常自作主张给个答案，而那种题的 reference 应该是「文档未提及」。

---

## 坑 13：`context_recall` 恒等于 1.0（标准差 0.0000）——最隐蔽的一个

| | |
|---|---|
| **现象** | 8 条全部 1.0，无一例外 |
| **根因** | **标准答案是自己证明自己**。`make_reference.py` 读「本次 TOP_K 召回的原文」起草答案 → 答案每句话必然在这几段里 → recall 去问"答案内容在上下文里找得到吗" → 当然全都找得到 |
| **解法** | `REF_TOP_K = 20`，起草时用 **top_k=20**（远大于正式评测的 TOP_K=5），让参考答案的信息面宽过正式召回面 |

**这是整个项目里最有价值的一个洞察**：

> 评测的前提是「尺子独立于被测对象」。用被测系统自己的输出造尺子，量出来必然满分。

**类比**：考试前把答案发给学生，考完发现全班 100 分。这个 100 分是真的，但衡量不了任何东西。

---

## 坑 14：修完 reference 后 recall 又饱和了（无法两全的 trade-off）

**现象**：为了修 recall，我删掉了 reference 里"不在召回原文里的内容"。修完 recall 从 1.0 变准了，但标准差又回到 0.035。

**根因**：**recall 没法同时做到「准确」和「有区分度」**。
- reference 写得准（只包含原文有的内容）→ 必然全被召回 → recall=1.0 饱和
- reference 写得宽（包含原文外的内容）→ 有区分度 → 但那些内容可能是模型编的

**怎么取舍**：**选准确**。饱和不是 bug，是结论——它说明你的 top_k=5 确实把该找的都找回来了。代价是 recall 不能再指导调参，那就换 `precision` 当主指标。

> **接受指标饱和，也是一种信息。** 它告诉你"这块没问题了，去查别的"。

---

## 坑 15：幻觉探针题会污染三个指标

**现象**：「公司有没有班车」「公司什么时候上市」这类题（文档里没答案），模型正确拒答，但分数很怪。

**根因**：它们会同时污染三个指标——

| 指标 | 拒答会造成 | 性质 |
|---|---|---|
| faithfulness | 没有实质 claim → 算出 **1.0** | 虚高，无意义 |
| answer_relevancy | 反推不出问题 → 分数很低 | **惩罚了正确的拒答行为** |
| context_recall | 不存在"该召回什么" → 必然 0 | 假警报 |

**解法**：从主评估剔除，**单独用「正确拒答率」衡量**——这才是幻觉探针题真正的价值。

**我自己的修正**：第一版提示写"仍参与 faithfulness"，这是错的（实际代码整个剔除了）。发现后纠正了，并把三条理由写清楚。

# 第四部分：模型层

---

## 坑 16：8b 当评委不可信

| | |
|---|---|
| **现象** | 分数忽高忽低 |
| **根因** | 8B 评委同一样本多次运行波动可达 **±0.2**，而一次调参的真实提升通常只有 **0.03~0.05**。**信号被噪声淹没** |
| **解法** | 评委换成更大的模型（14b / 32b / 云端 31b） |

**如果只能用小评委，四条纪律**：
1. 只信 **delta**，不信绝对值（绝不对外报"我们 faithfulness 是 0.91"）
2. 变化 <0.05 一律视为噪声
3. **评委必须 ≠ 生成器**（防自我评分膨胀）
4. 每次抽查最低分的 10 条，人工确认评委没胡说

**跨家族模型更好**：Gemma 评 Qwen，比 Qwen 评 Qwen 更没有风格偏好。

## 坑 17：Ollama 没有 rerank 端点

| | |
|---|---|
| **现象** | 配了 `bge-reranker-v2-m3`，调不通 |
| **根因** | **Ollama 官方 API 只有 generate/chat/embed，没有 `/api/rerank`**。官方模型库里 `bge-reranker` 是 404，能搜到的都是用户命名空间。而且 **Ollama 在模型不存在时也返回 404**——这个特性坑了我两次 |
| **解法** | 起独立的 rerank 服务（FastGPT 官方镜像 / Infinity / Xinference），或本地跑 sentence-transformers |

## 坑 18：FastGPT 里配 rerank 的三个坑

1. **API 密钥填 `ollama`**（任意非空值）——Ollama 默认不鉴权，这个字段只是表单必填
2. **`localhost:11434` 在 Docker 容器里指的是容器自己** → 改 `host.docker.internal`，并在 compose 加 `extra_hosts: - "host.docker.internal:host-gateway"`
3. **地址要带 `/v1`** → `http://host.docker.internal:11434/v1`

## 坑 19：`/api/chat` 返回 404 + `LossySetitemError`

| | |
|---|---|
| **现象1** | 调 Ollama 生成 404 |
| **根因1** | 旧版 Ollama 只暴露 `/api/generate`。**且它在模型不存在时也返回 404** |
| **解法1** | 自动回退 `/api/chat → /api/generate`；**读响应体区分两种 404**（"not found" = 模型不存在）；失败时**列出实际可用模型** |
| **现象2** | pandas 往列里塞字符串报 `LossySetitemError` |
| **根因2** | `reference` 列全空 → pandas 判成 **float64** → 往浮点列塞字符串，pandas 2.x 直接拒绝 |
| **解法2** | 写入前先 `astype(object)` |

## 坑 20：改了 JUDGE_MODEL 忘了改 REF_MODEL

**现象**：改了评委模型，跑 `make_reference.py` 还是报 `qwen3:14b not found`。

**根因**：config.py 里**两个**默认值都写成了 `qwen3:14b`，但功能完全不同（评委 vs 起草）。

**解法**：`REF_MODEL = ""` 留空 → 自动跟随 `JUDGE_MODEL`。**改一处就够**。

**顺带加的防线**：开工前 3 秒调 `/api/tags` 校验模型是否存在。以前是跑十几分钟后才 404，现在是开工即报错，还把可用模型列出来。

---

## 坑 21：`429 too many concurrent requests`

| | |
|---|---|
| **现象** | 云端评委打分时报并发超限 |
| **根因** | ragas 按「样本数 × 指标数」一次性派发：8条×4指标=**32 个并发请求**，云端扛不住 |
| **解法** | `EVAL_MAX_WORKERS = 1` + 遇到 429 自动等 60s 重试（云端限流窗口通常 60s） |

**代价**：并发降到 1 后 32 个任务串行，5~10 分钟。这是用云端评委（省 9GB 下载）换来的代价。

---

## 坑 22：Ollama 默认 num_ctx 只有 2048

**现象**：长上下文被**静默截断**，答案和判断都被悄悄破坏，且不报错。

**解法**：`NUM_CTX = 16384`。

**为什么危险**：它不报错，你只会觉得"分数莫名其妙偏低"。

---

## 坑 23：qwen3 默认开启思考模式

**现象**：输出里混着 `<think>...</think>`，消耗大量 token、变慢、吃光上下文。

**解法**：prompt 末尾加 `/no_think`，或在生成函数里正则剥离残留。

# 第五部分：指标层

---

## 坑 24：`DeprecationWarning` 满屏粉红字

**现象**：跑 `run_eval.py` 一堆红字，以为报错了。

**真相**：不是报错。ragas 在提示"这个写法以后会改"，**不影响当前打分**。

**关键**：**别照它改**。0.4.3 里新版 `ragas.metrics.collections` 反而跟 `evaluate()` 不兼容。所以警告只能屏蔽，不能跟。

---

## 坑 25：`faithfulness` 恒接近满分

| | |
|---|---|
| **现象** | 0.966~0.987，永远接近满分 |
| **根因** | **设计使然**。你的 prompt 强制"只用参考资料，禁止用自己的知识"，模型不可能编造。等于**提前告诉模型不许编，然后又去评它有没有编** |
| **结论** | 指标饱和 = 失去区分能力。接受它当**门槛指标**（≥0.95 即通过），别指望它指导调参 |

**想让它重新有区分度**，必须加让模型"想编"的题：
- 文档里根本没有答案的（幻觉探针，已有）
- **需要跨多个片段整合的**（容易漏、串）
- **数字/时间/名称细节题**（最容易记错）
- **两个相似概念的辨析题**（容易张冠李戴）

---

## 坑 26：NaN 让均值虚高

**现象**：`faithfulness` NaN 2/8（25%），均值却显示 0.987。

**根因**：pandas 算均值时**跳过 NaN**——0.987 是"6 条成功的均值"，不是 8 条的真实水平。**缺失的样本悄悄消失了**。

**解法**：
- 加重试 + 超时（`EVAL_MAX_RETRIES=4`、`EVAL_TIMEOUT=300`）
- 新增 NaN 明细输出，把没打成的样本**逐条列出来**
- 新增饱和检测（标准差 <0.01 标红）

---

## 坑 27：分不清是检索的锅还是生成的锅

**这是补齐四大指标的核心价值。** 归因矩阵：

| recall | precision | faithfulness | 结论 | 修法 |
|---|---|---|---|---|
| 低 | 低 | - | 检索整体不行 | 换中文 embedding |
| 低 | 高 | - | 漏内容 | 加大 TOP_K |
| 高 | 低 | - | 排序差 | **加 rerank** |
| 高 | 高 | 低 | 生成在编 | 换更大模型 |

**你的实际诊断**：第 8 条最相关的片段排在第 5 位，完全无关的"麦肯锡7S"排在第 3 位 → 典型的排序问题 → 该上 rerank。

## 坑 28：改了参数但看不到变化

**现象**：改完重跑，分数和上次一样。

**根因**：**忘了改 `VERSION`**。`DATA_OUT`/`SCORE_OUT` 都从 VERSION 推导，不改就是覆盖旧版。

**铁律**：**调一次参数，VERSION 就 +1**。旧版本不是垃圾，是对比基线。

---

## 坑 29：`make_reference.py` 不会创建数据集

**现象**：把 VERSION 改成 v2 后直接跑，报"找不到 eval_data_v2.xlsx"。

**根因**：它只**读写**已存在的文件，创建者是 `run_batch.py`。

**解法**：`new_version.py` 先克隆。三种模式：

| 模式 | 保留 | 适合 |
|---|---|---|
| `--ref-only` | 问题+上下文+回答，只清 reference | 改了 REF_TOP_K，只想重做答案 |
| `--regen` | 只留问题 | 改了 TOP_K / GEN_MODEL / prompt |
| 完整克隆 | 全部 | 只想重跑打分 |

**⚠️ 完整克隆的坑**：改了检索参数却用完整克隆，那份 contexts 是旧参数下的，跟旧版不可比。必须 `--regen`。

**第二次踩**：先改了 VERSION 再跑 `new_version.py v2`，脚本默认源版本 = VERSION = v2 = 目标本身 → "自己找自己"。**已加自动回退**：检测到源=目标时自动改用已有的最新版。

---

## 坑 30：调完 Excel 列宽跑一次脚本就没了

**根因**：`to_excel` 重写文件会**重置所有格式**。

**正确顺序**：先改内容，**最后**统一跑 `format_excel.py`（列宽 + 自动换行 + 行高 + 冻结首行首列）。

## 坑 31：分数表行号对不上 Excel 行号

**现象**：分数表第 4 条，在 Excel 里其实是第 6 行。

**根因**：2 道幻觉探针题被剔除出主评估，后面全部往前挪 2 位。

**教训**：**别按分数表位置去数 Excel 行**，会改错。按题目内容定位。

# 第七部分：关键决策的取舍逻辑（为什么这么做）

---

## 决策 1：自建向量库 vs 继续折腾 Open WebUI API

试过调 Open WebUI 的 `/api/v1/retrieval/query/collection`，卡在 token 获取（localStorage 里没有 `token` 键）、接口版本、返回结构三样都可能对不上。

**取舍**：放弃 API，自建。理由——
- API 依赖 token、接口版本、返回结构**三样外部变量**，任何一样不对就要重来
- 自建完全可控：contexts 是代码里的变量，想存哪存哪
- 而且它俩**共用同一个 Ollama**，不冲突

> **判断标准**：当你为一个外部依赖调试超过三轮，就该问"自建是不是更便宜"。

---

## 决策 2：不用 chromadb，用 numpy

**取舍**：几千块数据的规模，numpy 暴力检索毫秒级。chromadb 带来的是几百 MB 依赖 + 可能搞崩 ragas 环境 + 十几分钟安装时间。

> **判断标准**：技术选型看的是「你的数据规模」，不是「这个技术流不流行」。

---

## 决策 3：rerank 的两阶段检索（RETRIEVE_K=20 → TOP_K=5）

**为什么**：rerank 只改顺序、不改召回集合。所以候选池必须比最终数量大得多，否则 rerank 无从发挥。

**容错设计**：rerank 失败自动降级为纯向量检索，打印警告继续跑。**不中断整个流程**——这是关键的工程取舍：一个可选增强功能不该让主流程挂掉。

---

## 决策 4：开启 rerank 后相似度阈值要换

**原因**：cross-encoder 分数分布和余弦相似度完全不同（更极端，贴近 0 或 1）。沿用 0.45 会把几乎所有题误判成"文档未提及"。

**解法**：`SIM_THRESHOLD_RERANK = 0.1`，且 `make_reference.py` **读参数快照自动切换**，不用手动改。

> **通用教训**：换了一个组件的度量口径，所有依赖旧口径的阈值都要重新校准。

---

## 决策 5：Langfuse —— 接入后又全部移除

**接入理由**：补 Ragas 缺的「时间维度」——存链路、存分数、多版本对比、看线上真实流量。

**移除理由**：用户实际用不上，且增加了 `langfuse` / `openai` 依赖。

**认知澄清**：Langfuse **不替代** Ragas，也不替代自建向量库。Ragas 算分，Langfuse 存和比。官方就有集成方案，不是二选一。

---

# 第八部分：可复用的心法

---

### 1. 评测的价值不在分数，在于「改了参数分数变没变」

手工流程做不了这件事，所以必须脚本化。这是你绕了一大圈最终回到自建向量库的根本原因。

### 2. 拿到 0.98 先别高兴，问一句：它还有区分能力吗

饱和的指标等于没有指标。**标准差比均值更重要**——均值 1.0 标准差 0.0000，说明指标死了；均值 0.87 标准差 0.19，说明指标活着。

### 3. 先用 `show_answers.py` 肉眼看，再看分数

分数只有 0~1，看不出"回答是不是废话"；但你一眼就能看出来。476 字的回答配 57 字的标准答案，看数字是 6.6 倍，看一眼内容就知道尺子太窄。

### 4. 尺子必须独立于被测对象

用被测系统自己的输出造标准答案，量出来必然满分（recall 恒等于 1.0）。这是 REF_TOP_K 存在的全部理由。

### 5. 一次只改一个变量

这条最反直觉，也最容易违反。改两个你就不知道分数变化是谁造成的，等于白调。

### 6. 静默失败比报错危险十倍

空上下文、扫描版 PDF 提取出 0 字、num_ctx 截断、NaN 被均值跳过——**它们都不报错**。

### 7. 看「召回段数」比看「相似度」更快定位

10 个问题全都召回 1 段 = 库里只有 1 块。这个信号比 0.3 的相似度数值直白得多。

### 8. 接受饱和，也是一种信息

recall 饱和说明"该找的都找回来了"；faithfulness 饱和说明"prompt 管住了幻觉"。它们告诉你**这块没问题了，去查别的**。

# 第九部分：后来新增的能力（不是坑，是功能）

> 2026-11 之后陆续加的。每条写：**做了什么 / 为什么 / 代价**。
> 这些都不报错，但决定了这套东西能不能被日常使用 —— 坑让人停工，功能让人愿意用。

---

## 功能 1：一键启动 `启动控制台.bat`

**做了什么**：双击即启动，依次检查 venv → 向量库 → Ollama → 8501 是否占用（占则换 8502），打印本地/局域网两个地址，再拉起 Streamlit。

**为什么**：命令行 `python -m streamlit run app.py` 有四个坑：忘记激活 venv、PATH 里没有 streamlit、端口被占、控制台刷一堆彩色乱码。全部收进脚本里，用户只需要双击。

**取舍**：
- 脚本**必须 ASCII-only**（`chcp 65001` 也不能保证 cmd 正确解析中文）→ 所有提示语用英文，中文放在 Python 里打印
- 用 `--logger.hideWelcomeMessage true` 关掉 Streamlit 的 ANSI 横幅，地址改由 `show_urls.py` 打印
- 后来加了 `--server.headless true`（见坑 32），代价是**不再自动开浏览器**

---

## 功能 2：Streamlit 控制台（两个页面）

**做了什么**：
- **问答页**：流式回答 + 三段耗时（检索 / 首字 / 总时长）+ 引用原文汇总表（序号/文件夹/来源/分数/字数）+ 逐段展开与关键词高亮 + 文件夹筛选
- **参数与指标页**：指标卡片 → 参数面板 → 两种实验 → 历史表/走势图/最近两次对比

**为什么**：调参从「改 config → 跑命令行 → 等 40 分钟 → 记数字」变成「点两下 → 看曲线」。**尝试成本决定了你会不会真的去调参**。

**代价**：
- 多页要用 `st.navigation` + `st.Page`，`app.py` 只做导航
- 子线程不能碰 `st.session_state` / `st.cache_resource`（见坑 25 的 ScriptRunContext）
- 参数一热改，`Retriever` 就得重建 → 索引与 rerank 模型必须 `cache_resource` 兜住

---

## 功能 3：参数面板 → `data/ui_overrides.json`

**做了什么**：界面改的参数写进 `data/ui_overrides.json`；`config.py` 导入时读取并覆盖同名值（白名单 + 类型校验）。

**为什么**：不这么做会出现最难查的一类 bug —— **界面显示 `TOP_K=3`，命令行脚本还在用 5**。两套参数各跑各的，事后对比全是错的。

**取舍**：覆盖是**持久**的。跑正式实验前必须确认这个文件里的值；想还原就点「恢复 config 默认」或直接删文件。

---

## 功能 4：指标存档 `data/metric_runs.jsonl`

**做了什么**：每次实验追加一行：`run_id / 时间 / mode(retrieval|full) / version / source / n_samples / params 快照 / 四个指标 / 逐题明细 / note`。

**为什么**：多版本对比不能靠记忆。有了它，「上次 TOP_K=3 那组是多少来着」变成一次筛选；控制台的历史表、走势图、最近两次差值全都来自这个文件。

**取舍**：用 JSONL 不用 SQLite/Langfuse —— 一行一个实验、纯文本能 diff、能直接 `git diff` 看变化，零额外服务。

---

## 功能 5：两种实验（快速 vs 完整）

**做了什么**：
- **快速检索实验**：只重算 `context_recall / context_precision`，2~10 分钟
- **完整实验**：`run_batch → make_reference → run_eval`，约 1.5~2 小时，后台子进程跑（关页面不中断，关服务才中断）

**为什么**：Ragas 的检索侧两个指标只依赖「问题 + 上下文 + 参考答案」，**跟模型写出来的回答无关**。所以调 `TOP_K` / `RETRIEVE_K` / `rerank` / `BM25` 时完全可以跳过生成那一小时。

**代价**：快速实验没有 `faithfulness` / `answer_relevancy`（回答没重新生成，算了没意义）。界面上这两栏会是空的，属于预期。

---

## 功能 6：文档范围筛选（按 `docs/` 子文件夹）

**做了什么**：`build_index.py` 给每块写 `doc_dir` 元数据；检索时按选中的文件夹把范围外的相似度打成 `-inf`；界面支持单选/多选/全选/清空，提示语写明当前范围。

**为什么**：语料是按文件夹分主题的（方法论 / 客户文件 / 需求文档 / 行业报告）。业务经常问「只在这批需求文档里找」，全库检索会把方法论的内容混进来。

**取舍**：
- 判定靠**建库时写入的元数据**，所以旧索引要重建才有这个字段
- 只作用于问答页；实验页仍按全库（否则实验结果不可比）

---

## 功能 7：引用关键词高亮（不装 jieba）

**做了什么**：在「问题」和「原文」之间求**最长公共子串**，把命中的部分标黄。

**为什么**：装 jieba 只为高亮不值当；最长公共子串有个额外好处 —— **高亮出来的词一定真的出现在原文里**，不会出现"分词分错了但看起来很高亮"的假象。

**取舍**：措辞不同就匹配不到（问"得分"原文写"评分"），界面会明确提示「未在原文中匹配到关键词」，这是**预期行为**不是 bug。

---

## 功能 8：混合检索（BM25 + 向量 + RRF）

**做了什么**：
- `bm25.py`：纯标准库实现，**中文字符二元组 + 英文/数字整词**（`BLM模型是什么` → `blm` + `模型/型是/是什/什么`），不装 jieba
- `retrieval.Retriever` 变成三阶段：向量召回 + BM25 召回 → **RRF 融合名次** → rerank → TOP_K
- 参数：`HYBRID_ENABLED / HYBRID_RRF_K / HYBRID_VEC_WEIGHT / HYBRID_BM25_WEIGHT / BM25_K1 / BM25_B`

**为什么用 RRF 而不是分数加权**：BM25 分数没有上界、余弦在 0~1、cross-encoder 又是 sigmoid —— 三者量纲不通，直接相加等于**让「谁的量纲大」决定结果**。RRF 只看名次：`Σ w/(k+rank)`，量纲无关、零调参。

**为什么需要它**：向量检索对**缩写、专有名词、数字**常常失灵。同一句「IRR 二分法怎么算」：
- 纯向量 TOP3：组合分析、组合分析、**方法论·模型对比（完全不相关）**
- 混合 TOP3：组合分析里讲 IRR/二分法的那几段

**取舍（重要）**：在 v1 的 8 题**概念型**评测集上它**没有收益**（precision +0.006 在噪声内、recall 掉 0.125），所以**默认关闭**，只留开关。
但在**关键词型查询**上是明确更强的。这也是后来在 398 块新语料上要重测它的原因（行业报告里有大量数字与英文缩写）。

---

## 功能 9：全链路体检 `check_pipeline.py`

**做了什么**：把链路拆成 8 段单独测 —— 配置 / Ollama 服务 / 向量库（块数看这里）/ 单次 embedding / 单次生成 / rerank 实测 / 评测依赖 / 结论。每段都有超时。

**为什么**：出问题时最怕"不知道坏在哪"。8 段跑完，坏在哪一段一目了然，而且脚本自己不会卡死。

---

## 功能 10：rerank 模型下载兜底

**做了什么**：`predownload_rerank.py` 先试 `huggingface_hub`（关 Xet、走镜像），失败自动转**直连 HTTP + 断点续传**；两种都不行时提示 ModelScope。另加 `RERANK_LOAD_TIMEOUT=180s`，用 daemon 线程强制降级。

**为什么**：国内直连 huggingface.co 基本必超时，而且 `sentence-transformers` 下载卡住时**无法被打断**，界面会永远转圈。三层兜底 + 加载超时，保证最坏情况只是"没有 rerank"而不是"整个系统卡死"。

**实测**：hub 卡在大权重文件 0 字节；直连 2.3 MB/s（约 16 分钟）；ModelScope **33 MB/s，99 秒**。

---

## 功能 11：控制台噪音治理

**做了什么**：`ui_noise.py` 把 `streamlit.runtime.scriptrunner_utils.script_run_context` 的日志级别压到 ERROR；`--logger.hideWelcomeMessage` 关 ANSI 横幅；`disable_progress_bar()` 关掉 `Loading weights` 进度条。

**为什么**：控制台里三类噪音（`missing ScriptRunContext` 刷屏、`[34m` 乱码、`Loading weights 100%|███`）会把**真正的错误**埋掉。噪音不是"看着烦"，而是**降低了故障可见性**。

---

## 功能 12：彻底移除 langchain（含补丁的两次演进）

**做了什么**：
- `run_eval.py` 改成 Ollama 的 OpenAI 兼容接口（`/v1`）+ `openai` 客户端 + ragas 原生 `llm_factory`，**代码里一行 langchain 都没有**
- `ragas_compat.py` 负责"能让 ragas 被导入"：ragas 0.4.3 内部硬引用了一个新版依赖里已删除的子模块

**补丁的两次演进**（很能说明"写死 vs 自适应"）：
1. 第一版：把两个模块名**写死**在字典里，缺了就塞占位。能跑，但包一升级就失效，而且满屏都是那个第三方包的名字。
2. 第二版：**运行时自动补位** —— `import ragas` 抛 `ModuleNotFoundError` 时，读出缺的模块名，**只补"顶层包已装、但该子模块没了"的情况**；顶层包都没装就照常抛错（不掩盖真缺依赖）。

**为什么这么改**：写死意味着每次依赖变化都要改代码；自动补位既自适应又不会吞掉"真的没装"这种错误。

# 第十部分：后续新踩的坑

---

## 坑 32：管理员窗口启动 → Edge 弹「现有实例正在以提升的权限运行」

**现象**：双击 `启动控制台.bat`，控制台里明明已经 `Uvicorn server started on ::8501`，但屏幕中间弹出 Edge 的对话框问你「是否要用普通权限重启现有实例」。

**根因**：这个 bat 是**以管理员身份**运行的（窗口标题里就有"管理员"），而 Streamlit 默认启动时会**自动调浏览器**打开页面。管理员进程去调已经在普通权限下运行的 Edge → 权限不匹配 → Edge 弹窗。

**解法**：
1. 立刻可用：点「否」，手动打开 `http://localhost:8501`（服务其实已经起来了）
2. 根治：给 Streamlit 加 `--server.headless true`，**只监听、不碰浏览器**；地址由 `show_urls.py` 打印
3. 根本原因：这个项目不需要管理员权限（只写自己目录下的 `vector_store/`、`data/`）

**取舍**：失去"自动打开页面"，换来零弹窗。对着控制台里打印的地址点一下，比跟权限模型搏斗划算。

---

## 坑 33：rerank 在纯 CPU 上是 45 秒/题

**现象**：开 rerank 后，8 道题的检索从 0.6 秒变成 331~360 秒，20 道题要 12~15 分钟。

**根因**：cross-encoder 是**逐对**打分（问题 × 每个候选），`RETRIEVE_K=20` 就是 20 次前向。纯 CPU（i5-1135G7，4 核）就是这个量级；有 GPU 会小两个数量级。

**解法**：想快就降 `RETRIEVE_K`（20 → 12/8），**不要降 `TOP_K`** —— 时间花在候选池上，跟最终保留几段无关。

**取舍**：`TOP_K` 降到 3 只省 8% 时间，却真的丢内容（recall 1.000 → 0.875）。这笔交易在任何时候都不划算。

---

## 坑 34：`SEARCH_TIMEOUT=60` / `GEN_TIMEOUT=180` 太紧，误报"失败"

**现象**：界面偶发「检索超过 60s 未完成」「生成失败」，但其实任务在慢慢跑。

**根因**：超时值比真实耗还小 —— 开了 rerank 单次检索 45~56 秒；本地 8B「加载模型 + 预填充 2400 字上下文」要 2~4 分钟才出首字。

**解法**：`SEARCH_TIMEOUT=180`、`GEN_TIMEOUT=600`。

**取舍**：超时设大意味着真卡住时要多等；但"误杀正在跑的任务"比"多等两分钟"更糟。

---

## 坑 35：PowerShell 里 `set HF_ENDPOINT=...` 根本没生效

**现象**：设了镜像地址，`huggingface_hub` 依然去连官方源、依然超时。

**根因**：两层坑叠加 ——
1. PowerShell 里 `set` 是 `Set-Variable` 的别名，`set X=1` **不报错也不设环境变量**
2. 就算设对了，`HF_ENDPOINT` 也必须在 `import huggingface_hub` **之前**设进环境变量（这两个库在 import 时就把端点读成常量了）

**解法**：`$env:HF_ENDPOINT = "https://hf-mirror.com"`，且脚本内部按「先解析参数 → 设环境变量 → 才 import」的顺序写。

---

## 坑 36：rerank 下载卡在 0 字节 / `401 ... cas-server.xethub.hf.co`

**现象**：`huggingface_hub` 进度条一直 0%，或报 401 指向 `cas-server.xethub.hf.co`。

**根因**：hub 默认走 Xet 存储，镜像站没有鉴权；国内直连 huggingface.co 本身也不稳。

**解法**：`HF_HUB_DISABLE_XET=1` + 镜像 + 直连断点续传；都不行就 ModelScope。

**取舍**：不追求"一次装好"，而是"任何网络环境下都有退路"。

## 坑 37：混合检索在概念型题上反而掉召回

**现象**：开 BM25 后 8 题里 7 题分数一模一样，唯独「市场洞察有哪些模块」recall 从 1.0 掉到 0.0。

**根因**：RRF 融合后，**BM25 偏好的长关键词段落**挤掉了原先覆盖参考答案要点的那几段。向量那一路的第 5 名（≈0.0154）打不过"BM25 第 1 名 + 向量第 20 名"（≈0.0289）。

**解法**：默认关闭；想用就调 `HYBRID_BM25_WEIGHT`（0.5 更保守）。

**取舍**：这是一个**典型的"局部更准、整体更差"**的改动 —— 关键词查询明显变好，但整体 recall 掉了。数据上只能先关。

## 坑 38：语料被换掉 → 版本号与"可比性"同时失效

**现象**：重建库之后，`VERSION` 自动从 `v2` 跳到 `v3`；旧数据集还在，但和新库不可比。

**根因**：`COLLECTION` 由 `模型+chunk` 决定，**不含语料内容**；语料变了但库名没变，`build_index.py` 用「内容指纹」判断变化并自动 +1，避免版本号虚胀也避免新库覆盖旧结论。

**解法**：指纹变化才 +1；`config.py` 自动备份成 `config.py.bak.月日_时分秒`；数据集/分数按版本号分文件。

**取舍**：旧索引会被重建覆盖（**不可复活**），所以"当时跑出这个分数的上下文"只能从 `eval_data_vX.xlsx` 里看，不能重跑。

## 坑 39：评委输出被截断 → 某条样本的 `faithfulness` 永远是 NaN

**现象**：`faithfulness` 均值 0.963，但 NaN 比例 6.25%（16 条里 1 条）。这一条**重打两次仍是 NaN**。

**根因**：ragas 报 `IncompleteOutputException` —— 评委输出的 JSON 被截断（回答长、要判断的陈述多），解析失败。重试也一样，因为每次都在同一个长度上被截断。

**解法**（还没做）：调大评委的 `max_tokens`，或换一个更稳的评委，或降低单次判断的陈述数。

**取舍**：NaN 会被 `mean()` 跳过，所以**均值看起来是好的，但样本覆盖不全**。这正是"NaN 让均值虚高"那条坑的延续。

## 坑 40：0 分不一定是评委抖动 —— 重打两次还是 0

**现象**：两条 `answer_relevancy = 0.000`，怀疑是评委随机。

**验证**：单独把这两条重打一遍 → **仍然 0.000**。

**根因**（两条不一样）：
- 「市场洞察对比」：回答里写"MM 流程（未在资料中明确定义）"，属于**对冲式回答**，被判答非所问
- 「SPAN/FAN/PDC」：模型直接拒答（15 字）

**取舍**：这说明 0 分是**真实缺陷**，不是测量噪声。别急着换评委，先看回答本身。

## 坑 41：跨文档对比题被"最强的那个来源"吸走

**现象**：问「BLM / 五看 / MM 流程在市场洞察上有什么异同」，回答里只有 BLM 和五看，MM 那句是"未在资料中明确定义"。

**诊断**（宽召回 vs 窄召回逐层拆）：
- 关键内容**确实在库里**（`MM方法论.html`），但 rerank 只给它 **0.025 分、排第 17**
- 换成混合检索，前 5 名**一个没变**
- 但用子查询「MM 市场管理流程 环境分析 竞争分析 市场分析 公司自身分析」→ 直接把它捞到 **余弦 0.719、第 1 名**

**根因**：单查询的语义被**最强的那个来源**（提到"市场洞察"最多的 BLM 系列）占满了。rerank 是单调打分，没有"多样性"机制，于是 5 个名额全给了同一个主题。

**解法**：**查询拆分（multi-query）** —— 对比型问题拆成子查询，各检各的，再合并去重。

**取舍**：这是架构级改动（不是调参），但它是目前唯一被数据证实的解法。同类问题里也有"只差一名"的（SPAN/FAN/PDC 的块 rerank 第 6、`TOP_K=5` 切掉），那种只要 `TOP_K` +1 就行 —— **两种病，别用一种药**。

## 坑 42：PowerShell 重定向把 UTF-8 日志写成 UTF-16 乱码

**现象**：用 `*>> log.txt` 收集脚本输出，中文全变成"每字之间夹空格"的乱码。

**根因**：PowerShell 的 `*>>` 走 `Out-File`，解码子进程输出时用的是控制台编码，再按 UTF-16 落盘；Python 侧虽然已经强制 UTF-8 输出，但在 PowerShell 这一层就被破坏了。

**解法**：用 `Start-Process -RedirectStandardOutput <file>`（**原始字节直写**，不经 PowerShell 解码）。

**取舍**：牺牲了"边跑边看"（要 tail 文件），换来日志可读。

## 坑 43：`.ps1` 被执行策略挡住

**现象**：`& .\xxx.ps1` 报「未对文件进行数字签名，无法在当前系统上运行」。

**根因**：默认执行策略是 `Restricted/AllSigned`。

**解法**：改用 `pwsh -Command "<inline 脚本>"` 直接跑（本例就是这么绕的），或 `-ExecutionPolicy Bypass`。

**取舍**：inline 没法复用；但对一次性编排足够，而且不改变机器全局策略。

# 第十一部分：语料三次变化，指标"复活"

**这一节是本项目最重要的方法论收获**：recall 从"永远 1.0"变成"有区分度"，靠的不是调参，是**扩语料 + 扩题库**。

| 版本 | 语料 | 题库 | recall | precision | faithfulness | relevancy |
|---|---|---|---|---|---|---|
| v1（10-23 前） | 165 块 / 3 文件夹 | 8 条可答 + 2 探针 | **1.000（饱和）** | 0.928 | 0.974 | 0.925 |
| v2（11-05 上午） | 75 块 / 2 文件夹 | 同上 | 未评（语料被删减，仅重建索引） | — | — | — |
| **v3（11-05 下午）** | **398 块 / 2 文件夹** | **16 条可答 + 4 探针** | **0.927** | 0.900 | 0.963（15/16） | 0.771 |

**v3 的三个关键事实**：

1. **recall 活过来了**：逐题出现 0.500 / 0.667 / 1.000 三档。之前"恒等于 1.0"不是检索完美，是**尺子到头了**（语料太小 + 参考答案太窄）。
2. **relevancy 掉到 0.771**，但**剔除那两条跨文档对比题后是 0.882** —— 掉分是结构性的，不是普适退化。
3. **4 条幻觉探针全部正确拒答**（余弦 0.277 / 0.319 / 0.339 / 0.459，全部低于 `SIM_THRESHOLD=0.45`），而真问题的余弦在 0.585~0.840 —— 门禁阈值站得住。

**评测链路耗时实测（398 块 / 20 题，纯 CPU）**：

| 环节 | 实测 |
|---|---|
| 建库 | 16.1 分钟（2.68 秒/块） |
| `run_batch`（检索 + 生成） | 86 分钟（4.3 分钟/题） |
| `make_reference`（云端起草） | 13.4 分钟 |
| `run_eval`（4 指标） | 正常约 5~10 分钟；有评委超时重试时会到 73 分钟 |
| **合计** | **约 3 小时 10 分** |

### 坑 44：`COLLECTION` 名里没有 `overlap` → 建库静默覆盖

**现象**：`config.py` 写着 `CHUNK_OVERLAP=100`，但 `vector_store` 里的库是 483 块（overlap=200 的产物）。

**根因**：`COLLECTION = f"kb_{model}_{CHUNK_SIZE}"` —— 只按模型和 chunk 分库，overlap 不在名字里。
改 `CHUNK_SIZE` 会安全地新建一个库；改 `CHUNK_OVERLAP` 会**原地覆盖**同一个库。

**解法**：重建（15.8 分钟）；根治是把 overlap 拼进 collection 名，或建库后在 meta 里校验实际参数并报警。

**取舍**：分库越细，磁盘上越多"看起来能复用、其实参数不同"的库；
但静默覆盖的代价更大 —— 你会在错误的前提上得出所有结论。

### 坑 45：`ui_overrides.json` 残留会污染整机参数

**现象**：一个跑实验的队列在夜里被杀，第二天发现 `config.COLLECTION` 变成了 `kb_bge-m3_latest_800`，
但参数面板上没改过任何东西。

**根因**：队列在"写 overrides"之后、"删 overrides"之前被杀，文件留在了磁盘上。
`config.py` 导入时无条件读取它，于是**之后每条命令都用 bge-m3**，包括你以为在跑基线的那些。

**解法**：脚本用 `try/finally` 保证恢复；队列第一步先删残留；日志里打印"当前生效参数"。

**取舍**：overrides 让"前端与 CLI 参数一致"变简单，代价是它是个**隐藏的全局状态**。
凡是全局状态，都必须能在启动时被打印和清除。

### 方法论收获：口径不齐会制造假结论

`chunk=500` 在旧口径下 precision 只有 0.787，补齐"用新索引重新起草参考答案"后是 0.864 ——
差 0.076，三倍于噪声。不做严格口径就会误判成"500 块差很多"；
真实差距只有 0.037，且仍不如 800 的 0.900。

> 一句话：换语料 / 换切法 / 换模型时，**参考答案必须跟着重起草**，
> 否则你量的是"尺子没对齐"，不是"系统变差了"。

## 附四：换 embedding 模型的三个连带效应（2026-11-06）

把默认 embedding 从 `qwen3-embedding:0.6b` 换成 `bge-m3` 后，跑了完整四指标基线（v4）。
三个连带效应比"分数涨了还是跌了"更值得记住。

### 效应 1：绝对余弦阈值不能跨模型复用

| | 真问题余弦 | 探针余弦 | 是否重叠 |
|---|---|---|---|
| qwen3-embedding | 0.585 ~ 0.840 | 0.277 ~ 0.459 | 不重叠，`SIM_THRESHOLD=0.45` 很干净 |
| bge-m3 | **0.515 ~ 0.737** | **0.461 ~ 0.580** | **重叠** |

bge-m3 把余弦整体压进更窄的区间。后果：
- `SIM_THRESHOLD=0.45` 对 4 条探针**全部失效**（4/4 越过阈值）
- 真问题里最低的 0.515 已经贴到探针上限 0.580

**教训**：任何"余弦 < X 就低置信"的规则，X 必须按模型重新标定，不能写死。
比阈值更稳的是**相对信号**（top1 与 top2 的差距、rerank 分数）。

### 效应 2：参考答案重起草会让"同一套指标"失去可比性

v4 的 precision 是 0.829，v3 是 0.900 —— 看着是退化 0.072。
但 v4 的参考答案也是用新库**重新起草**的。干净的同参考 A/B 是 K4：precision +0.009、recall +0.021。

**教训**：跨版本比分数之前，先问一句"参考答案是不是同一份"。
不是同一份，就只能比"各自与自己参考答案的匹配度"，不能比绝对值。

### 效应 3：换模型会改变"哪类题吃亏"

同一道「市场洞察 BLM/五看/MM 异同」：

| | precision | recall | relevancy |
|---|---|---|---|
| v3 | 1.000 | 0.667 | **0.000（答非所问）** |
| v4 | **0.200** | **1.000** | **0.910（切题）** |

bge-m3 终于召回了 MM 流程的内容（recall 到 1.0、回答变切题），代价是 5 段里混进更多只沾边的片段。
**它不是"更好"或"更差"，而是把错误从"答不出来"换成了"答得出来但夹杂噪声"。**

> 一句话：换 embedding 不是调一个参数，是换了一把尺子和一套取舍。
