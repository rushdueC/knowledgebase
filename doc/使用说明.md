## 1. 这是什么

一套**纯 numpy 向量库 + Ragas 打分**的本地 RAG 评测工具链，加上一个 Streamlit 控制台。
它要回答的问题只有一个：**改了一个参数，分数到底变好了没有？**

```
docs/ 原始文档
   │  build_index.py      切块 + embedding + 落盘（vector_store/）
   ▼
向量库（.npy 向量 + .json 文本与元数据）
   │  run_batch.py        检索 + 生成回答 → data/eval_data_vX.xlsx
   ▼
数据集（问题 / 检索到的上下文 / 回答 / 标准答案）
   │  make_reference.py   起草标准答案（人工过一遍）
   │  run_eval.py         Ragas 四指标打分 → data/scores_vX.csv
   ▼
指标 → compare.py / 控制台「参数与指标」页 / data/metric_runs.jsonl 存档
```

### 和 Open WebUI 的关系

两者**共用同一个 Ollama**，但向量库各一份，互不干扰：

| | Open WebUI | 本套件 |
|---|---|---|
| 用途 | 日常聊天、盲测选模型 | 跑评测、调参数 |
| 检索原文 | ❌ 界面只给文件名 | ✅ 直接是代码变量 |
| 调参方式 | 点界面 + 重建索引 | 改 config / 界面改参数 |
| 知识库 | 界面上传 | 把文件丢进 `docs/` |

### 换电脑部署：还需要 Open WebUI 吗？

**做评测不需要，只装 Ollama 就行。**

| 组件 | 必需？ | 作用 |
|---|---|---|
| Ollama | ✅ | 提供 embedding + 生成 + 评委模型 |
| Python 环境 | ✅ | 跑脚本 |
| 本套件 | ✅ | 建库 / 跑批 / 打分 / 对比 / 控制台 |
| Open WebUI | ❌ | 只是聊天界面 |
| Docker | ❌ | 只是为了跑 Open WebUI |

Open WebUI 唯一不可替代的价值是**模型盲测（Arena）**：人工点赞投票、Elo 排名，回答
「哪个模型用着顺手」。那是主观偏好评测，给**人**用的，Ragas 替代不了。

## 2. 环境准备

### 2.1 装 Ollama 并拉模型

```powershell
ollama pull qwen3:8b                 # 被评测的生成模型
ollama pull qwen3-embedding:0.6b     # 中文 embedding（639MB，必装）
ollama pull gemma4:31b-cloud         # 评委（云端，需要能连 ollama.com）
```

验证：

```powershell
ollama list                          # 能看到上面三个
curl http://localhost:11434/api/tags
```

> 想完全离线：把 `JUDGE_MODEL` 换成已装的本地模型（例如 `qwen3:8b`），
> 同时把 `GEN_MODEL` 换成 `qwen3:4b`，保证**评委 ≠ 选手**。

### 2.2 建 Python 环境

```powershell
cd knowbase
python -m venv .venv
.\.venv\Scripts\activate

pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple   # 国内源，必做
pip install -r requirements.txt
```

`requirements.txt` 已经包含：requests / numpy / pandas / openpyxl、pypdf / python-docx /
python-pptx（格式支持）、ragas==0.4.3 + openai（评测）、streamlit（界面）、
sentence-transformers + huggingface_hub（rerank）。

### 2.3 评测依赖只需要两个包

```powershell
pip install ragas==0.4.3 openai
```

> 评委和向量模型都走 Ollama 的 OpenAI 兼容接口（`/v1`），
> 用 `openai` 客户端 + ragas 原生 `llm_factory`，不需要额外装别的东西。
> `ragas_compat.py` 里有一个很小的导入补丁（ragas 内部引用了新版依赖里已移除的模块），
> 由 `run_eval.py` 自动加载，你不用处理。

验证（先加载补丁再导入 ragas；在项目目录下执行）：

```powershell
.\.venv\Scripts\python.exe -c "import ragas_compat; ragas_compat.install(); import ragas; print('ragas OK')"
```

### 2.4 支持的文档格式

| 格式 | 需要装包 |
|---|---|
| `.txt` `.md` | ❌ 不用 |
| `.html` `.htm` | ❌ 不用（标准库解析） |
| `.pdf` | `pypdf` |
| `.docx` | `python-docx` |
| `.pptx` | `python-pptx` |
| `.xlsx` | ❌ 不支持，把内容复制进 txt |

> 缺包时 `build_index.py` 会在最后醒目汇总「哪些文档没被读进来」——
> 别只看「共 N 块」，那份汇总才是关键。

### 2.5 换电脑时要拷什么

- ✅ 整个工具包目录（脚本）
- ✅ `docs/` 所有原始文档
- ✅ `questions.txt` 问题集
- ⬜ **不用拷 `vector_store/`**（新机器重建更稳，避免路径/版本不兼容）
- ⬜ 不用拷 `data/`（除非想保留历史指标；`data/metric_runs.jsonl` 是纯文本，可带走）

## 3. 快速开始（6 步）

```powershell
python build_index.py     # ① 文档 → 切块 → 向量库
python run_batch.py       # ② 检索 + 生成 → data/eval_data_v1.xlsx
python show_answers.py    # ③ 肉眼看回答（重要，别跳过）
python make_reference.py  # ④ 起草标准答案 → 人工改一遍（要检索指标才需要）
python run_eval.py        # ⑤ Ragas 打分
python compare.py         # ⑥ 多版本对比
```

### 每一步的「成功标志」

**没看到对应输出就别往下走。**

| 步骤 | 正确输出 | 不对怎么办 |
|---|---|---|
| ① `build_index` | `共 398 块 \| 维度 1024` | 块数 0 → `docs/` 没文档；块数 1 → 只有占位文件 |
| ② `run_batch` | 余弦相似度 >0.7、回答 150~400 字 | 相似度 <0.45 → 检索没命中，看第 9 节 |
| ③ `show_answers` | 回答有实质内容、不全是拒答 | 全是拒答 → prompt 太严或检索错 |
| ④ `make_reference` | 每行写出标准答案或「文档未提及」 | 报「没有可用样本」→ 先跑 ② 和 ④ |
| ⑤ `run_eval` | 四指标出分，NaN <5% | 全 1.0 → 指标饱和；全 0 → 数据空 |
| ⑥ `compare` | 有 v1/v2 两行 | 只有一行 → 忘了升 `VERSION` |

### 本机当前基线（v3，2026-11-05 实测）

语料 **18 份 / 398 块**（战略规划方法论 15 份 198 块、行业报告 3 份 200 块），题库 20 条（16 + 4 探针），
`TOP_K=5` + rerank 开：

| 指标 | v3 基线 | 备注 |
|---|---|---|
| faithfulness | **0.963** | 15/16 有效，1 条评委输出截断（稳定 NaN） |
| answer_relevancy | **0.771** | 被 2 条跨文档对比题拖累，剔除后 0.882 |
| context_recall | **0.927** | 逐题 0.50~1.00，**不再饱和** |
| context_precision | **0.900** | 逐题 0.33~1.00 |

> 历史参考（v1，165 块 / 8 题）：faithfulness 0.974、relevancy 0.925、recall 1.000（饱和）、precision 0.928。
> 两种语料不可横向比较，只有"同语料同题目只改一个参数"的差值可信。

## 4. 脚本一览

| 脚本 | 干什么 | 什么时候用 |
|---|---|---|
| `build_index.py` | 文档 → 切块 → 向量库 | 首次 / 改了 chunk、embedding、文档 |
| `run_batch.py` | 批量检索 + 生成回答 → 数据集 | 每次调参后 |
| `make_reference.py` | 起草标准答案 | 要跑检索侧两个指标时 |
| `run_eval.py` | Ragas 打分 | 每次调参后 |
| `compare.py` | 多版本分数对比 | 有 ≥2 个版本后 |
| `show_answers.py` | 看完整问答原文 | 打分**之前**先肉眼看 |
| `check_pipeline.py` | 全链路体检（8 段） | 卡住 / 报错时**第一个**跑 |
| `check_data.py` | 数据体检 | 分数异常时第一步 |
| `diagnose_scores.py` | 分数诊断（高分是真是虚） | 拿到分数后 |
| `versions.py` | 管理各版本产物 | 版本多了要清理 |
| `rerank.py` | 验证 rerank 是否生效 | 开 rerank 后 |
| `predownload_rerank.py` | 预下载 rerank 模型 | 第一次用 rerank |
| `enable_rerank.py` | 一键改 config 开 rerank | 懒得手改配置 |
| `app.py` | 控制台入口 | `streamlit run app.py` |
| `page_chat.py` / `page_metrics.py` | 控制台两个页面 | 由 `app.py` 导航 |
| `pipeline_runner.py` | 完整实验的后台驱动器 | 由控制台调用 |
| `启动控制台.bat` | 双击启动 | 日常使用 |

> `run_batch.py` 的 `VERSION` 会自动 +1（内容指纹变化时），不用手改。

## 5. 前端控制台

### 5.1 启动

**方式一：双击 `启动控制台.bat`（推荐）**

它会依次检查：`.venv` 在不在 → `vector_store/` 在不在 → Ollama 通不通 →
8501 端口占没占（占了自动换 8502），然后打印地址并启动，浏览器自动打开：

```
------------------------------------------------------------
  Local URL    : http://localhost:8501
  Network URL  : http://192.168.110.220:8501   (同一局域网的其他设备可用)
------------------------------------------------------------
```

> 想放桌面：右键 `启动控制台.bat` → 发送到 → 桌面快捷方式。

**方式二：命令行**

```powershell
cd knowbase
.\.venv\Scripts\python.exe -m streamlit run app.py
```

（不激活 venv 也能跑；`python -m streamlit` 比直接 `streamlit` 稳，不依赖 PATH。）

> 前提：Ollama 在跑；已建过库。要跑「检索实验」还需要已有数据集和标准答案。

### 5.2 两个页面

入口 `app.py` 只做导航，页面是 `page_chat.py` / `page_metrics.py`
（用 `st.navigation`，可直接深链 `/chat`、`/metrics`）。

**💬 问答页**

| 区域 | 内容 |
|---|---|
| 顶部参数 chip | `GEN_MODEL / TOP_K / RETRIEVE_K / rerank / 温度 / 向量库`，一眼看出改没改 |
| 📁 文档范围 | 按 `docs/` 子文件夹筛选检索范围：单选 / 多选 / 全选 / 清空 |
| 首屏空状态 | 居中标语「让知识，可被召回」+ 语料规模 + 4 个示例问题按钮 + 能力卡片 |
| 回答 | 流式输出，边生成边显示 |
| 耗时 | 检索 ms · 首字 ms · 总秒数 · 生成速度（字/秒） |
| 引用原文 | 「序号 / 文件夹 / 来源 / 分数 / 字数」汇总表 + 逐段展开（关键词高亮） |
| 清空对话 | 有对话时显示「🧹 清空对话」 |

> 示例问题取自 `questions.txt` 前几条（长度 ≤30 字）。想让首屏推荐哪几题，
> 直接调 `questions.txt` 的顺序。

**📊 参数与指标页**（四块，从上到下）

1. 最近一次实验的指标卡片
2. 🎛️ **参数面板**：`TOP_K / RETRIEVE_K / RERANK_ENABLED / GEN_MODEL / TEMPERATURE / JUDGE_MODEL`
3. 🧪 **跑一次实验**：快速检索实验 / 完整实验（两个 Tab）
4. 📈 **指标存档与对比**：历史表 + 走势图 + 最近两次的差值与参数差异

### 5.3 文档范围筛选（只搜某个文件夹）

| 操作 | 效果 |
|---|---|
| 不选（默认） | 在**全部文档**里检索 |
| 选 1 个 | 只在这个文件夹里检索 |
| 选多个 / **全选** | 在选中的文件夹里检索（全选 = 等同不筛选） |
| **清空** | 取消筛选，回到全部文档 |

- 判定依据是「块来自哪个文件夹」（建库时写进 `doc_dir`），不会跨文件夹混进来
- 检索提示会写明范围：`① 正在检索…（限定 需求文档）`
- 选中范围里一条都检索不到时会明确提示，不会静默返回空
- ⚠️ 旧索引要重跑一次 `build_index.py` 才有 `doc_dir`（内容没变，`VERSION` 不会 +1）
- ⚠️ 只作用于问答页；实验页仍按全库检索

### 5.4 在前端改参数

| 勾选「同步到命令行脚本」 | 效果 |
|---|---|
| ✅ 默认 | 参数写进 `data/ui_overrides.json`，**CLI 脚本也读这套值** |
| ❌ | 只在当前界面生效，CLI 用 `config.py` 的值 |

`config.py` 在导入时读这个文件（白名单 + 类型校验，写坏也不会崩），
所以「界面显示的参数」和「脚本跑的参数」不会打架。

- 还原：点「↩️ 恢复 config 默认」（会删掉覆盖文件）
- 也可以手动删 `data/ui_overrides.json`
- ⚠️ 它是**持久的**：下次 `python run_batch.py` 也会用这套值，跑正式实验前先确认

`EMBED_MODEL` / `CHUNK_SIZE` / `CHUNK_OVERLAP` 改了必须重建库，所以页面上只展示不热改。

### 5.5 指标存档

每次实验写一行到 `data/metric_runs.jsonl`：

```json
{"run_id": "20261102-184024-28f3", "ts": "2026-11-02 18:40:24",
 "mode": "retrieval", "version": "v1", "source": "ui", "n_samples": 8,
 "params": {"TOP_K": 5, "RETRIEVE_K": 20, "RERANK_ENABLED": true, ...},
 "metrics": {"context_recall": 1.0, "context_precision": 0.9033},
 "note": "A · TOP_K=5 rerank开"}
```

页面上可以：看历史表（指标 + 参数并列）、走势折线图、「最近两次对比」
（指标差值 + 这两次之间改了哪些参数）、导出 `metric_runs.csv`、清空存档。

> 判读口径和 CLI 一致：**|差值| < 0.05 基本算噪声**。

### 5.6 两种实验怎么选

| | ⚡ 快速检索实验 | 🐢 完整实验 |
|---|---|---|
| 跑什么 | 只重新检索 + 重算 `context_recall / context_precision` | `run_batch → make_reference → run_eval` |
| 指标 | 只有检索侧两个 | 四个都有 |
| 实测耗时 | 2~10 分钟 | 40~60 分钟 |
| 怎么跑 | 页面里同步跑（有进度条） | 后台子进程（关页面不中断，关服务会中断） |
| 状态/日志 | 结果直接写存档 | `data/experiment_status.json` / `data/experiment.log` |

**为什么快速实验能省略生成**：Ragas 的这两个指标只依赖
「问题 + 检索到的上下文 + 标准答案」，**跟模型写出来的回答无关**。
所以改 `TOP_K` / `RETRIEVE_K` / `RERANK_ENABLED` 时用它最快。
代价是 `faithfulness` / `answer_relevancy` 留空（回答没重新生成，算了没意义）。

实测时间构成（8 题）：纯向量检索 0.6 秒；开 rerank 约 331~360 秒；
云端评委 137~211 秒。所以开 rerank 时"快速"是相对 40 分钟而言的。

### 5.7 检索链路与混合检索

```
问题 ──┬─→ 向量召回（余弦）  ──┐
       │                        ├─→ RRF 融合候选池（RETRIEVE_K）──→ rerank ──→ TOP_K 段
       └─→ BM25 召回（关键词）──┘        ↑ 这两步都可以单独关掉
```

- **向量召回**：语义相近就能找到，怕的是缩写/专有名词/数字
- **BM25 召回**（`bm25.py`，纯标准库）：只认字面命中，正好补上一条的短板
- **RRF 融合**：只看名次不看分数（`Σ w/(k+rank)`），因为三种分数（余弦 / BM25 / cross-encoder）量纲完全不同
- **rerank**：在合并后的池子里用 cross-encoder 精排（可选）

开关都在 config（也可以在前端「参数与指标」页改）：

```python
HYBRID_ENABLED = True      # 关掉 = 纯向量
HYBRID_BM25_WEIGHT = 1.0   # 想让关键词更强势就调大，如 1.5
```

> 实测：同一句「IRR 二分法怎么算」，纯向量的 TOP3 里有一段完全无关的「方法论·模型对比」，
> 混合检索后 TOP3 全是组合分析文档里讲 IRR 的段落。
> 详细对比与参数说明见 [参数手册.md](参数手册.md) 的「混合检索」一节。

其它小知识：

- **关键词高亮**：在「问题」和「原文」之间找最长公共子串，不装 jieba。
  好处是高亮出来的词一定真的出现在原文里；措辞不同（问"得分"原文写"评分"）就匹配不到，
  界面会提示「未在原文中匹配到关键词」，这是**预期行为**。
- **检索链路只有一份实现**：`retrieval.py` 的 `Retriever`。问答页、实验引擎、
  `run_batch.py` / `make_reference.py` 都调它，所以前端调参和命令行调参不会有两套行为。
- **改高亮颜色**：`page_chat.py` 顶部的 `HL_COLOR = "#FFE066"`。

## 6. 加 rerank

### 6.1 什么时候该加

`context_recall` 高、`context_precision` 低 —— 内容都检到了，只是排得乱，加 rerank 收益最大。
两个都低说明是**召回**问题，该先换 embedding。

### 6.2 三步加上

```powershell
python predownload_rerank.py    # ① 预下载模型（约 2.2GB）
# ② config.py 确认四行（脚本结束会打印，默认已配好 local 后端）
python rerank.py                # ③ 验证：必须看到 ✅ 和两行分数
```

配置长这样（`predownload_rerank.py` 跑完会直接打印）：

```python
RERANK_ENABLED    = True
RERANK_BACKEND    = "local"
RERANK_MODEL      = "BAAI/bge-reranker-v2-m3"
RERANK_LOCAL_PATH = str(BASE / "models" / "bge-reranker-v2-m3")
```

### 6.3 然后必须重跑数据

```powershell
python run_batch.py         # ⚠️ 必须重跑，retrieved_contexts 变了
python make_reference.py    # 门禁用余弦相似度，和 rerank 无关
python run_eval.py
python compare.py           # 只盯 context_precision 的 delta
```

### 6.4 实测收益（2026-11-02，8 题快速检索实验）

| 配置 | recall | precision | 检索耗时 |
|---|---|---|---|
| TOP_K=5 rerank 关 | 0.875 | 0.815 | 0.6 s |
| TOP_K=5 rerank 开 | **1.000** | **0.903** | 360 s |
| TOP_K=3 rerank 关 | 0.875 | 0.875 | 0.6 s |
| TOP_K=3 rerank 开 | 0.875 | 0.927 | 331 s |

- precision 收益 **+0.089**，约是同配置重复跑噪声（0.0245）的 **3.6 倍** → 真实有效
- 代价：纯 CPU 上每題 **+45 秒**（有 GPU 会小两个数量级）
- 收益集中在「把对的排前面」：组合分析题 0.45→0.83、BCG 题 0.75→1.00、
  「市场洞察模块」题 recall 从 0 救回 1.0；只有 TAM/SAM/SOM 一题轻微变差（1.00→0.92）
- 逐题对比见 [README.md](../README.md) 第 8 节

### 6.5 三个必须知道的行为

1. **失败会自动降级**为纯向量检索，主流程不中断；但降级是静默的，
   所以开 rerank 后一定要先 `python rerank.py` 验证过再跑数据。
2. **只改顺序不改召回集合**，`context_recall` 基本不动，盯 `context_precision`。
3. **加载/下载有超时兜底**（`RERANK_LOAD_TIMEOUT=180s`），卡住会自动降级；
   但真正的解法永远是先 `predownload_rerank.py`。

### 6.6 模型下载：三种方式自动兜底

`predownload_rerank.py` 会先试 `huggingface_hub`，失败自动转**直连 HTTP + 断点续传**。
本机实测：hub 卡在大权重文件 0 字节；直连能到 2.3 MB/s（约 16 分钟）。
两种都卡的时候用 ModelScope（实测 33 MB/s，99 秒下完）：

```powershell

python -c "from modelscope import snapshot_download; snapshot_download('BAAI/bge-reranker-v2-m3', local_dir=r'models\bge-reranker-v2-m3')"
python rerank.py
```

三个后端怎么选：

| 后端 | 需要 Docker | 需要下载模型 | 国内可用 |
|---|---|---|---|
| 关 | ❌ | ❌ | ✅ |
| local（默认） | ❌ | ✅ 2.2GB（脚本带镜像/直连/ModelScope 兜底） | ✅ |
| http | ✅ | 服务端下 | ✅ |

http 后端（需 Docker）：

## 7. 评测口径：指标怎么读

### 7.1 四个指标

| 指标 | 评什么 | 需要 reference | 健康值 |
|---|---|---|---|
| `faithfulness` | 回答有没有编造 | ❌ | 0.85~0.95（≥0.95 视为饱和） |
| `answer_relevancy` | 有没有答到点上 | ❌ | >0.8 |
| `context_recall` | 该检的有没有检到 | ✅ | 越高越好 |
| `context_precision` | 检到的排得靠前吗 | ✅ | 越高越好 |

只跑前两个，你只能说"回答有问题"，**说不出是检索的锅还是生成的锅**。

### 7.2 诊断矩阵与归因

| precision | recall | faithfulness | 结论 | 修法 |
|---|---|---|---|---|
| 低 | 高 | - | 检到了但排后面 | **加 rerank** 或减小 chunk |
| 高 | 低 | - | 漏内容 | 加大 `TOP_K` 或减小 chunk |
| 高 | 高 | 低 | 检索没问题，生成在编 | 换更大 `GEN_MODEL` / 收紧 prompt |
| 低 | 低 | - | 检索整体不行 | 换中文 embedding |
| 高 | 高 | 高 | 健康 | 加更难的题 |

`run_eval.py` 和 `diagnose_scores.py` 都会自动输出归因结论。

### 7.3 reference 怎么写（三条铁律）

1. **用文档原文措辞**，不要自由发挥 —— 否则评委认为"上下文里缺内容"，误判成检索失败
2. **只写答案要点**，1~3 句话，不加"根据资料"这类前缀
3. **文档没答案的题写「文档未提及」**（这时模型拒答才是对的）

`make_reference.py` 会起草草案并标 `ref_is_draft=True`，**必须人工过一遍**：
模型会写错、写漏，尤其在"文档里没有答案"的题上自作主张给答案。

> `make_reference.py` 用 `REF_TOP_K=20` **重新检索**来起草，而不是用评测时的 TOP_K 段。
> 否则参考答案的每句话必然能在那几段里找到 → `context_recall` 恒等于 1.0，指标失效。

### 7.4 指标饱和：为什么 v1 全是 1.0，v3 又不饱和了

v1 的 `context_recall` 是 **1.000（8 条全满分）**，这不是检索完美，而是：

- 语料只有 165 块，`REF_TOP_K=20` 已经覆盖全库 12%
- reference 被要求"1~3 句话"，信息面没有明显宽于 TOP_K 的召回

**v3 扩到 398 块 + 20 道题之后，recall 回到 0.927，逐题出现 0.50 / 0.667 / 1.00 三档** —— 指标重新有了区分度。
所以「recall 饱和」的正解不是降 `TOP_K`，而是**把语料和题库都做大**。

**但把 `TOP_K` 降到 3 依旧不划算**（见 §6.4 和 [README.md](../README.md) 第 8 节）：
v1 上 recall 1.000 → 0.875（真漏了内容），precision +0.024 在噪声内，耗时只省 8%。
**想提速请降 `RETRIEVE_K`，不要降 `TOP_K`。**

### 7.5 题库怎么出（决定评测价值）

**10~20 条起，分四类**（比例是经验值）：

| 类型 | 占比 | 例子 | 检测什么 |
|---|---|---|---|
| 文档里直接有答案 | 40% | "BCG矩阵分哪几类" | 基础检索 |
| 需跨片段整合 | 30% | "SWOT和PESTEL怎么结合" | 多路召回 |
| **文档里没有答案** | 20% | "公司有班车吗" | **会不会瞎编** ← 最重要 |
| 易混淆 | 10% | 两个相似概念的区别 | 检索精度 |

`questions.txt` 格式：**只要问题，一行一条**，不要表头、逗号、引号。

```
有哪些常见的战略规划模型
SWOT分析和PESTEL分析怎么结合使用
公司有没有提供班车
```

四列格式（`user_input / retrieved_contexts / response / reference`）是**输出**，
由 `run_batch.py` 自动生成，不用手写。

> 题库越小，指标越"粗"：8 题时 recall 的刻度是 0.125，很多参数的效应会被噪声吞掉。
> 想让实验有分辨率，先把题库扩到 20~30 题。

### 7.6 幻觉探针题的口径

`questions.txt` 里应该有 20% 是"文档里根本没有答案"的题（例如"公司有没有提供班车"）。
它们**不参与**检索侧指标（不存在"该召回什么"，硬算必然 0 分，是假警报），
但**参与** `faithfulness` —— 那才是它们存在的意义。开关是
`EXCLUDE_NO_ANSWER_FROM_RETRIEVAL = True`。

### 7.7 评委可信度

- 8B 级评委同一样本多次运行波动可达 ±0.2，而调参的真实提升常常只有 0.03~0.05
- ✅ **只信 delta，不信绝对值**；变化 <0.05 视为噪声
- ✅ 评委模型必须 ≠ 生成模型（防自我评分膨胀）
- ✅ NaN 比例 >5% 说明评委崩了（调大 `EVAL_MAX_RETRIES` 或换更大的评委）
- 实测：云端 `gemma4:31b-cloud` 同配置重复跑，precision 只差 **0.0245** —— 这就是噪声量级

## 8. 日常迭代循环

```
① config.py（或界面）改一个参数
   （build_index.py 会按内容指纹自动把 VERSION +1，不用手改）
        ↓
② python build_index.py    ← 只在改了 chunk / embedding / 文档时需要
③ python run_batch.py
④ python show_answers.py   ← 先肉眼看，别急着看分数
⑤ python make_reference.py ← 数据集变了就重新起草
⑥ python run_eval.py
⑦ python compare.py        ← v2 vs v3
        ↓
   有用吗？→ 留着；没用 → 回滚，换个参数再试
```

### 铁律

> **一次只改一个变量，改完立即对比。**
> 改两个你就不知道分数变化是谁造成的。

### 版本号怎么走

- 建库时如果**知识库内容真的变了**（内容指纹不同），`VERSION` 自动 +1 并备份 `config.py`
- 重复建库（内容没变）不会 +1，避免版本号虚胀
- 想手动控制：`python build_index.py --no-bump`，或 `AUTO_BUMP_VERSION = False`
- ⚠️ 旧版脚本建的索引没有内容指纹，第一次重跑不会 +1，那次请手动改

### 参数记录表（自己维护，别靠脑子记）

| 版本 | chunk | top_k | rerank | 嵌入模型 | faithfulness | relevancy | 改了什么 |
|---|---|---|---|---|---|---|---|
| v1 | 800 | 5 | 开(local) | 0.6b | 0.974 | 0.925 | 历史基线（165 块，8 题） |
| **v3** | 800 | **5** | 开(local) | 0.6b | **0.963** | **0.771** | 当前基线（398 块，20 题，recall 0.927 / precision 0.900） |
| — | 800 | 5 | 关 | 0.6b | — | — | rerank 关（只有检索指标 0.875/0.815） |
| — | 800 | 3 | 开(local) | 0.6b | — | — | top_k 5→3（0.875/0.927，实测更差） |

### 调参优先级（按性价比）

| 顺序 | 改什么 | 预期收益 |
|---|---|---|
| 1 | embedding 换 `qwen3-embedding:0.6b` | 中文检索提升最大 |
| 2 | `RERANK_ENABLED` 开 + local 后端 | precision 低、内容排得乱时收益最大（实测 +0.089） |
| 3 | `TOP_K` 5~8 | 答案不完整时 |
| 4 | `RAG_SYSTEM_PROMPT` 放宽 | 回答过短、过度拒答 |
| 5 | `CHUNK_SIZE` | 召回片段总是差一点或太啰嗦 |
| 6 | `JUDGE_MODEL` 换更大 | 分数波动太大、NaN 高 |
| 7 | `GEN_MODEL` 换更大 | 检索没问题但回答质量差 |

> 每个参数的作用、当前值、坑，见 **[参数手册.md](参数手册.md)**；

## 9. 排查手册

### 9.1 出问题先跑体检

```powershell
python check_pipeline.py
```

它把链路拆成 8 段单独测，**每段都有超时，保证自己不会卡死**：

```
① 配置文件      ② Ollama 服务      ③ 向量库（chunk 数看这里）
④ 单次 embedding    ⑤ 单次生成    ⑥ rerank 实测
⑦ 评测依赖（ragas / openai / 评委模型）    ⑧ 结论
```

### 9.2 常见坑总表

| 症状 | 原因 | 解法 |
|---|---|---|
| `找不到向量库 xxx` | 没建库 / 参数改了换了 collection | `python build_index.py` |
| 检索到 0 段 | `docs/` 是空的；或文档范围选得太窄 | 放文档 / 点「清空」取消筛选 |
| 回答全是 15 字、相似度 0.3 | `docs/` 里没有真实文档，或格式包没装 | 装 pypdf/python-docx/python-pptx，重建库后块数应 >50 |
| 分数全是 NaN | 评委太弱 / 输出不合规 | 换更大的 `JUDGE_MODEL`（要支持 tools）+ 调大 `EVAL_MAX_RETRIES` |
| 分数接近 1.0 但明显不对 | 评委 = 生成器，自我评分膨胀 | `JUDGE_MODEL` 必须 ≠ `GEN_MODEL` |
| `faithfulness` 全是 1.0 | system prompt 强制只用资料，指标饱和 | 加幻觉探针题 / 细节题 |
| `answer_relevancy` 全是 0.0 | 回答为空或全是拒答 | `python check_data.py` 定位 |
| 改了参数看不到变化 | 忘了升 `VERSION`，新结果覆盖旧的 | 靠自动 +1，或手动改 |
| `UnicodeDecodeError: 0x90` | 把 `.xlsx` 改成 `.csv` 后缀，实际还是 ZIP | 用 `pd.read_excel()`，**永远别用 Excel「另存为 CSV」** |
| `ParserError: Expected 1 fields` | Excel 按区域设置用分号/制表符 | 改用 xlsx，一劳永逸 |
| `NameError: Path not defined` | `import` 写在了文件中间 | **所有 import 放文件最顶部** |
| pip 装 chromadb 极慢 | 会拉 onnxruntime/tokenizers/fastapi 几百 MB | **本套件不用 chromadb**，numpy 暴力余弦，小库毫秒级 |
| Ollama 默认 num_ctx 2048 | 长上下文被**静默截断** | `NUM_CTX = 16384` |
| 加 rerank 后回答变慢 | cross-encoder 逐对打分 | 降 `RETRIEVE_K`（20→10~12），别降 `TOP_K` |
| 换嵌入模型报维度错误 | collection 维度锁定 | 正常现象，`COLLECTION` 已自动换名，重建库即可 |
| 脚本一重定向就 `UnicodeEncodeError` | Windows 管道模式退回 GBK | `config.py` 已统一把 stdout 改成 UTF-8 |
| `pandas.errors.LossySetitemError` | pandas 3.x 把全空的 `reference` 列推断成 float64 | `make_reference.py` 已强制该列为 object + NaN 换空串 |
| 回答里出现 `（注：<arg_key:...>…）` | 旧版把一串来历不明的控制串拼进 prompt | 已改为 Qwen3 官方 `/no_think` |
| rerank 一直显示「降级」 | 模型没下载 / 路径不对 | `python predownload_rerank.py`，再 `python rerank.py` |
| rerank 下载报 `401 ... cas-server.xethub.hf.co` | hub 默认走 Xet，镜像没鉴权 | 脚本已自动设 `HF_HUB_DISABLE_XET=1` |
| 导入 ragas 报 `ModuleNotFoundError: <某个子模块>` | 该子模块在新版依赖里已被移除 | 用 `run_eval.py` / `check_pipeline.py` 跑（会自动加载 `ragas_compat.py`，只补「包已装、子模块没了」的情况） |

### 9.3 界面卡在「检索中…」—— 多半是 rerank 本地后端

**现象**：一直转圈，日志里有 `WinError 10060` / `huggingface.co/.../.modules.json`。

**根因**：`RERANK_BACKEND="local"` 首次调用要加载本地 cross-encoder；
若 `RERANK_LOCAL_PATH` 目录不存在，会退化成去 HuggingFace 下载，而国内直连基本必超时，
下载线程还无法被打断。

**止损**：`RERANK_ENABLED = False`，或在控制台把「启用 rerank」的勾去掉再应用。

**已内置的三层保护**：

1. **本地目录优先**：路径存在就完全离线加载，绝不联网
2. **HF 镜像 + 关 Xet**：`HF_ENDPOINT=hf-mirror.com`，且在 import 之前设好
3. **加载超时**：`RERANK_LOAD_TIMEOUT=180s` 后强制降级（daemon 线程实现）

### 9.4 PowerShell 里 `set HF_ENDPOINT=...` 根本不生效

| shell | 正确写法 |
|---|---|
| cmd | `set HF_ENDPOINT=https://hf-mirror.com` |
| **PowerShell** | **`$env:HF_ENDPOINT = "https://hf-mirror.com"`** |

在 PowerShell 里用 cmd 的 `set` 写法**不会报错，但变量也没设上**
（PowerShell 的 `set` 是 `Set-Variable` 的别名）。

还有第二个坑：**必须在 `import huggingface_hub` 之前设** ——
这两个库在 import 时就把端点读成常量了。
所以 `predownload_rerank.py` 的顺序是「先解析参数 → 设环境变量 → 才 import」。

### 9.5 控制台里的那几行「警告」

**`Thread '检索-worker': missing ScriptRunContext!`**
Streamlit 的线程上下文警告。为了做超时保护，检索/生成放在子线程里跑，
而子线程不该碰 `st.session_state` / `st.cache_resource`。
**已修**：`Retriever` 在主线程构造、生成参数在主线程读好再传进去，
并用 `ui_noise.py` 把这条日志级别压到 ERROR 兜底。

**`[34m`、`[0m` 这些乱码**
Streamlit 启动横幅的 ANSI 颜色码，你的控制台没开 VT 渲染。
**已修**：启动脚本加了 `--logger.hideWelcomeMessage true`，改由 `show_urls.py`
打印纯文本地址。想看彩色输出就用 **Windows Terminal**，或执行一次：

```powershell
reg add HKCU\Console /v VirtualTerminalLevel /t REG_DWORD /d 1 /f
```

**`Loading weights: 100%|████████| 393/393`**
transformers 加载 rerank 模型的进度条。**已关闭**
（`rerank.py` 里调用了 `disable_progress_bar()`，HF 下载进度条也一并关掉）。

### 9.6 超时相关的两个参数

| 参数 | 默认 | 现象 |
|---|---|---|
| `SEARCH_TIMEOUT` | 180s | 开了 rerank 后单次检索约 45~56 秒，设 60 会误报「检索超过 60s 未完成」 |
| `GEN_TIMEOUT` | 600s | 本地 8B「加载模型 + 预填充 2400 字上下文」可能 2~4 分钟，设 180 会误判「生成失败」 |

### 9.7 其它已知限制

| 现象 | 说明 |
|---|---|
| 快速实验没有 `faithfulness` / `answer_relevancy` | 回答没重新生成，这两项算了没意义 |
| 快速实验报「没有可用的样本」 | 数据集 `reference` 为空，先跑 `make_reference.py` 并人工确认 |
| 改了 `REF_TOP_K` 后 recall 没变 | 需要重跑 `make_reference.py` 才会重新起草 |
| 实验页不读「文档范围」筛选 | 目前只作用于问答页 |
| 一句话问答等好几 分钟 | 本地 8B 在 CPU 上就是 3~5 分钟/题；换云端或 qwen3:4b |

### 10.3 Langfuse 接入（可选）

它和 Ragas 是**互补**关系：Ragas 算分，Langfuse 存链路 / 存分数 / 做多次实验对比 / 看线上流量。
本目录没有内置 `langfuse_eval.py`（旧文档提到过，文件并不存在），要用需要自己写一层。

关键设计点（如果自己接）：

1. `task` 必须返回 dict（`{"answer": ..., "contexts": ...}`），只返回字符串算不出分
2. Ollama 走 OpenAI 兼容接口：`OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")`
3. SDK v4 改了 API：`set_current_trace_io` / `start_as_current_observation` /
   `propagate_attributes(tags=[...])`
4. 脚本结束前必须 `langfuse.flush()`，否则数据发不出去
5. 本地 Ollama 并发要压低（`max_concurrency=2`）

> 本套件的 `data/metric_runs.jsonl` 已经能承担"多版本对比"这件事，
> 不想装 Langfuse 的话，控制台的「指标存档与对比」就够用。

### 10.4 附：Open WebUI 里的检索参数（如果你还在用它）

路径：管理员面板 → 设置 → 文档

| 参数 | 默认 | 建议 |
|---|---|---|
| 文本分割器 | 字符 | 改 **Token** |
| Markdown 标题分割 | - | **开** |
| Chunk Size | 1000 | 800~1000 |
| Chunk Overlap | 100 | 100~200 |
| **Embedding Model** | all-MiniLM-L6-v2 | **改 qwen3-embedding:0.6b**（中文必改） |
| Top K | 3 | 3~5 |
| 混合搜索 | 关 | **开** |
| **相关度阈值** | 0 | **保持 0**（调高会静默过滤掉正确答案） |

三个坑：① 改了 Embedding / Chunk 必须点 **Reindex**；② 换 embedding 会维度冲突，
要删库重建；③ 相关度阈值别设高 → 正确答案被打 0.65 分也会被过滤。

> 这套是 Open WebUI 自己的检索链路，和本套件的 `vector_store/` **互不影响**。

### 10.5 一句话心法

> **评测的价值不在分数本身，而在于「改了一个参数、分数变了没有」。**
> 拿到 0.98 别高兴——先问一句：它还有区分能力吗？
