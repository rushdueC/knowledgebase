# 这里一大堆参数，都是些啥玩意？

> 这份文档回答「**参数**」相关的一切：
> **① 每个参数的作用 / 当前值 / 谁在读它 / 改了会怎样**
> **② 哪些参数真的影响指标（影响矩阵）**
> **③ 已经测过什么、接下来该测什么（实验台账）**
>
> 怎么装、怎么跑、界面怎么用、出问题怎么查 → 见 **[使用说明.md](使用说明.md)**。
> 项目定位与调参记录 → 见 **[README.md](../README.md)**。
>
> ⚠️ 别把这份文件放进 `docs/`：那个目录会被 `build_index.py` 索引进向量库，
> 变成检索的噪声源，污染你自己的评测。

---

## 0. 改参数前，先回答两个问题

**问题一：这个参数在哪一层？** 决定你要重跑多少东西。

| 层 | 参数 | 改完必须重跑 |
|---|---|---|
| 知识层 | `EMBED_MODEL`、`CHUNK_SIZE`、`CHUNK_OVERLAP` | `build_index.py` → `run_batch.py` → `make_reference.py` → `run_eval.py`（全套） |
| 召回层 | `TOP_K`、`RETRIEVE_K`、`RERANK_*` | `run_batch.py` → `make_reference.py` → `run_eval.py`（**不用**重建库） |
| 生成层 | `GEN_MODEL`、`TEMPERATURE`、`NUM_CTX`、`DISABLE_THINK`、`RAG_SYSTEM_PROMPT` | `run_batch.py` → `run_eval.py`（reference 可以先不动） |
| 测量层 | `JUDGE_MODEL`、`REF_TOP_K`、`EXCLUDE_NO_ANSWER_*` | `run_eval.py`（`REF_TOP_K` 还要重跑 `make_reference.py`） |
| 工程层 | 超时 / 路径 / 版本 | 一般不用重跑 |

**问题二：这个参数被哪个脚本读？** 每个参数都标了「谁读它」。
只被 `page_chat.py` 读的参数（例如 `SEARCH_TIMEOUT`）改了**只影响界面**，
命令行评测完全不受影响 —— 这类最容易白改。

**一条铁律：一次只改一个变量**，否则你不知道指标变化是谁造成的。

## 1. 参数全景：46 个参数里真正该动的只有 14 个

记号：成本 ⚡ = 快速检索实验（2~10 分钟）｜🐢 = 完整实验（约 40 分钟）｜🏗️ = 还要重建库。
状态：✅ 已测（有数据）｜⬜ 未测。

### 层 1 · 知识层（改了要重建库，`COLLECTION` 会变，旧数据集不可比）

| 参数 | 当前 | 影响 | 成本 | 状态 |
|---|---|---|---|---|
| `EMBED_MODEL` | qwen3-embedding:0.6b | 召回质量的根本上限（本机另装 bge-m3 可对比） | 🏗️ | ⬜ |
| `CHUNK_SIZE` | 800 | 片段粒度：太小丢上下文，太大稀释相关性 | 🏗️ | ⬜ |
| `CHUNK_OVERLAP` | 100 | 边界处信息是否被切断 | 🏗️ | ⬜ |

### 层 2 · 召回层（只影响 `context_recall / precision`，可以用 ⚡ 快速实验）

| 参数 | 当前 | 影响 | 成本 | 状态 |
|---|---|---|---|---|
| `TOP_K` | 3 | 喂给模型几段：多则 recall↑ precision↓ | ⚡ 9.5 min | ✅ 5 vs 3 |
| `RETRIEVE_K` | 20 | 召回候选池：多则 precision↑ 但更慢 | ⚡ 9.5 min | ⬜ |
| `HYBRID_ENABLED` | True | 开 BM25 关键词召回，和向量用 RRF 融合 | ⚡ 秒级（BM25 不花钱） | ✅ 开 vs 关（见 §3） |
| `HYBRID_BM25_WEIGHT` | 1.0 | 融合时 BM25 的话语权（关键词更强势就调大） | ⚡ | ⬜ |

| `RERANK_MODEL` | bge-reranker-v2-m3 | 排序模型强度（base 570MB / v2-m3 2.2GB） | ⚡ + 下载 | ⬜ |

| `TEMPERATURE` | 0.0 | 评测必须 0（可复现），不该拿它做实验 | — | 固定 |

| 参数 | 当前 | 影响 | 成本 | 状态 |
|---|---|---|---|---|
| `JUDGE_MODEL` | gemma4:31b-cloud | 测量工具的精度/偏差 | 🐢 5 min（只打分） | ⬜ 对比 qwen3:8b |
| `REF_TOP_K` | 20 | **直接决定 recall 的口径**：起草参考答案时检索多宽 | 🐢（重跑 make_reference + 打分） | ⬜ |
| `REFERENCE_PROMPT` | 1~3 句 | 参考答案的详细程度 → 影响 recall | 🐢 | ⬜ |

### 层 5 · 工程层（不影响质量，只影响「跑不跑得动」）

`OLLAMA_URL`、`SEARCH_TIMEOUT`、`GEN_TIMEOUT`、`RERANK_TIMEOUT`、`RERANK_LOAD_TIMEOUT`、
`RERANK_BATCH_SIZE`、`HF_ENDPOINT`、`RERANK_LOCAL_PATH`、`VERSION`、`AUTO_BUMP_VERSION`、

**这些不要当实验变量**，它们是基础设施。唯一值得测的是 `RERANK_BATCH_SIZE`（性能，不是质量）。

## 2. 参数卡片

### A. 路径与位置

| 参数 | 当前值 | 作用 | 谁读它 |
|---|---|---|---|
| `BASE` | 本文件所在目录 | 所有相对路径的锚点，脚本可以随便移动位置 | 几乎全部脚本 |
| `DOCS_DIR` | `BASE/docs` | **知识库源文件目录**（txt/md/pdf/docx/pptx/html），递归扫描 | `build_index.py`、`check_data.py` |
| `DB_DIR` | `BASE/vector_store` | 向量库落盘位置（`.npy` 向量 + `.json` 文本与元数据） | `build_index.py`、`retrieval.py`、`run_batch.py` 等 |
| `DATA_DIR` | `BASE/data` | 数据集、分数、指标存档、实验状态/日志都在这 | 大多数脚本 |
| `QUESTIONS` | `BASE/questions.txt` | 评测问题集，**一行一条，只要问题不要答案** | `run_batch.py`、`check_data.py` |

> ⚠️ 三件不要做的事：
> ① 不要把分析笔记放进 `docs/`（会被索引成检索噪声）；
> ② 不要手动改 `vector_store/` 里的文件（维度/行数对不上会静默出错）；
> ③ 换电脑时 `docs/` 要拷、`vector_store/` 可以不拷（重建更快更稳）。

### B. 三个模型（都跑在 Ollama 上）

#### `OLLAMA_URL` = `http://localhost:11434`

本地 Ollama 服务地址。所有 embedding、生成、评委调用都走它。
改成远程地址（比如另一台带 GPU 的机器）也能用，但 RAG 的每一步都会经过网络。

#### `EMBED_MODEL` = `qwen3-embedding:0.6b` ⭐ 影响最大

把文本变成向量（1024 维）的模型。**它决定了检索能力的上限**：模型选错，后面怎么调都救不回来。

- 中文必须用中文/多语言模型；英文默认模型（all-MiniLM 之类）在中文上几乎不可用
- **它被写进了向量库名字**（`COLLECTION = kb_{模型}_{chunk}`）→ 换模型会自动建新库，
  不会维度冲突，但旧数据集不可比
- 备选：`bge-m3`（本机已装，1024 维，中文也强）
- 谁读它：`build_index.py`、`retrieval.py`、`run_eval.py`（answer_relevancy 用它算相似度）等

#### `GEN_MODEL` = `qwen3:8b` ⭐ 被评测的对象

真正写答案的模型。它的产出直接决定 `faithfulness`（有没有编）和 `answer_relevancy`（有没有答到点）。

- 本机 CPU 上 **3~5 分钟一题**（实测），是整条流水线最慢的一环
- 换小模型（`qwen3:4b`）大约快一倍，但回答质量会掉
- 换成云端模型（如 `gemma4:31b-cloud`）会快很多，但就不再是「本地部署评测」
- 谁读它：`run_batch.py`、`page_chat.py`、`run_eval.py`（记录用）、`compare.py`

#### `JUDGE_MODEL` = `gemma4:31b-cloud` ⭐ 打分的人

Ragas 用它判断「这句话能不能被上下文支撑」「这条上下文相关吗」。

- **必须 ≠ `GEN_MODEL`**，否则就是选手自己判卷，分数会虚高
- 必须支持工具调用（tools）—— ragas 的结构化输出依赖它；`ollama list` 里
  capabilities 带 `tools` 的才行
- 本地 8B 评委波动可达 ±0.2；云端大模型稳得多（实测同配置重复跑，precision 只差 0.0245）
- **它不影响你的系统，只影响你看到的数字** —— 别把它当调参项
- 谁读它：`run_eval.py`、`experiment.py`、`check_pipeline.py`（检查是否已安装）

### C. 切块（建库时定生死）

#### `CHUNK_SIZE` = `800`

每个向量块的最大字符数。中文 500~1200 都合理。

- 太小 → 一个概念被切碎，答案缺上下文（recall 掉）
- 太大 → 一块里混进无关内容，向量被"稀释"（precision 掉）
- **写进了向量库名字**：改它 = 新建一个库，必须重跑 `build_index.py`，旧数据集作废
- 谁读它：`build_index.py`、`run_batch.py`（记录用）

#### `CHUNK_OVERLAP` = `100`

相邻块之间重叠的字符数，防止一句话正好被切在边界上。

- 经验值：`CHUNK_SIZE` 的 10%~20%
- 调大 → 边界信息更完整，但库变大、检索变慢
- **不写进库名**（所以改它不会换 collection，但仍需重建库才生效）
- 谁读它：`build_index.py`

> 切块策略本身写死在 `build_index.py` 的 `split_text()` 里：
> 优先在 `\n\n` / `\n` / `。` / `！` / `？` / `；` / `. ` 处断开，找不到才硬切。

### D. 检索（召回宽度）

#### `TOP_K` = `3` ⭐ 已经实测过，但数据说 5 更好

最终**喂给生成模型几段**上下文。

- 调大 → recall 涨（该有的内容更容易被包含）、precision 掉（更多无关内容）、prompt 变长
- 调小 → 反过来，但可能直接漏掉关键内容
- 📊 实测（同 8 题，rerank 开）：`5` 时 recall 1.000 / precision 0.903；
  `3` 时 recall 0.875 / precision 0.927。**precision 那点提升在噪声内，recall 掉的是真的**
  → 数据上 **5 更好**（当前 config 按要求设为 3，想回滚改成 5 即可）
- ⚠️ 改 `TOP_K` **几乎不省 rerank 的时间**（耗时在候选池 `RETRIEVE_K` 上）
- 谁读它：`retrieval.py`（核心）、`run_batch.py`、`page_chat.py`、`make_reference.py`

#### `RETRIEVE_K` = `20` ⭐ rerank 的成本开关

开 rerank 时，先向量粗排拿出多少个候选，交给 cross-encoder 精排。

- 必须 ≥ `TOP_K`
- 调大 → 精排有更多选择，precision 可能更好，但**耗时线性上涨**（20 个候选 ≈ 45 秒/题）
- 调小 → 快，但可能连正确答案都没进候选池
- 想提速：**优先降这个**（20 → 10~12），而不是降 `TOP_K`
- 不开 rerank 时这个参数不生效
- 谁读它：`retrieval.py`、`run_batch.py`、`page_chat.py`

#### 混合检索（BM25 + 向量）：`HYBRID_ENABLED` = `True`

在向量召回之外**再加一路 BM25 关键词召回**，两路各自排名后用 RRF 融合成候选池，
后续 rerank / 取 TOP_K 都基于这个合并后的池子。

**为什么需要**：向量擅长「语义相近」，但对**缩写、专有名词、数字、代码式片段**常常失灵。
实测同一句「IRR 二分法怎么算」：

| 检索方式 | TOP3 结果 |
|---|---|
| 纯向量 | 组合分析（0.499）、组合分析（0.474）、**方法论·模型对比（0.425，无关）** |
| 混合 | 组合分析×2、组合分析（含 IRR 的那段）、方法论（RRF 分低） |

BM25 那一路直接把「写着二分法/IRR 的段落」顶到最前面。

**融合为什么用 RRF**（`retrieval.rrf_fuse`）：
`score(d) = Σ w_i / (k + rank_i)`，只看名次不看绝对分。
因为 BM25 分数没上界、余弦在 0~1、cross-encoder 又是另一套分布，
直接相加等于让「谁的量纲大」决定结果。

相关参数：

| 参数 | 当前 | 说明 |
|---|---|---|
| `HYBRID_ENABLED` | `True` | 总开关。关掉 = 纯向量（做对照实验用） |
| `HYBRID_RRF_K` | `60` | RRF 平滑常数，60 是论文默认值，一般不动 |
| `HYBRID_VEC_WEIGHT` | `1.0` | 向量那一路的权重 |
| `HYBRID_BM25_WEIGHT` | `1.0` | BM25 那一路的权重，想让关键词更强势就调大（如 1.5） |
| `BM25_K1` | `1.5` | 词频饱和：越大越「同一个词出现多次就占便宜」 |
| `BM25_B` | `0.75` | 长度惩罚：0=不惩罚，1=完全按长度归一 |

**中文分词**（`bm25.py`）：不装 jieba，用「字符二元组 + 英文/数字整词」——
`"BLM模型是什么"` → `["blm"] + ["模型","型是","是什","什么"]`。
不需要词典，对「关键词命中」够用；代价是 term 变多（398 块约几十万个，内存仍无压力）。

**成本**：BM25 建索引约几十毫秒、查询毫秒级 —— 相比 rerank 的 45 秒/题可以忽略。
但注意**它不省钱也不提速**：融合只是让候选池更准。

⚠️ 两个容易混的点：
1. **开了混合后，数据集里的 `top1_similarity` 是 RRF 分数**（0.0x 量级），
   既不是余弦也不是 cross-encoder 分数。门禁/诊断仍然看 `top1_vector_similarity`（永远是余弦）。
2. 融合只在**召回**阶段；`TOP_K` 仍由 rerank（若开）或 RRF 排序决定。

- 谁读它：`retrieval.py`、`bm25.py`、`run_batch.py`、`page_chat.py`、`experiment.py`

#### `SEARCH_TIMEOUT` = `180`

界面上「检索」这一步最多等多少秒，超时就报错提示而不是无限转圈。

- **只影响 Streamlit 界面**，命令行脚本不读它（脚本各自有自己的 `timeout=`）
- ⚠️ 开了 rerank 之后别再设 60：实测单次检索（20 个候选逐个过 cross-encoder）
  在纯 CPU 上约 **45~56 秒**，机器一忙就会误报「检索超过 60s 未完成」
- 谁读它：`page_chat.py`

#### 文档范围筛选（不是 config 参数，但在检索层）

界面上「📁 文档范围」选中的文件夹，会作为 `doc_dirs` 传给 `retrieval.Retriever`，
检索时把范围外的相似度置为 `-inf`。

- 它**不是**常驻配置：不选 = 全部文档，选择只存在当前会话里
- 判定依据是 chunk 元数据里的 `doc_dir`（建库时写入），所以旧索引要重跑
  `python build_index.py` 才有这个字段
- 只作用于问答页；`run_batch.py` / 实验引擎目前按全库检索

### E. rerank（重排）

#### `RERANK_ENABLED` = `True`

总开关。关掉就是纯向量检索。

- 📊 实测（8 题、TOP_K=5）：precision `0.815 → 0.903`（+0.089，约 3.6 倍噪声）、
  recall `0.875 → 1.000`
- 代价：纯 CPU 上每題 **+45 秒**
- 关掉时打分照常跑（会自动走纯向量路径），是很好的 A/B 对照组
- 谁读它：`rerank.py`、`retrieval.py`、`run_batch.py`、`page_chat.py`

#### `RERANK_BACKEND` = `"local"`

`"local"`（本地 cross-encoder，不用 Docker）/ `"http"`（独立服务）/ 其它值 = 视为关闭。

#### `RERANK_MODEL` = `"BAAI/bge-reranker-v2-m3"`

精排模型。

- v2-m3：多语言，效果好，约 **2.2 GB**
- `BAAI/bge-reranker-base`：约 **570 MB**，更小更快，中文效果略弱
- `http` 后端时，这个名字必须和服务端的 `MODEL_NAME` 一致

#### `RERANK_LOCAL_PATH` = `BASE/models/bge-reranker-v2-m3`

本地模型目录。**这个目录存在就完全离线加载，绝不联网**。

- 目录不存在时会**明确报错并降级**（不会偷偷去下载）
- 用 `python predownload_rerank.py` 会自动下到这里
- 想换模型只改 `RERANK_MODEL` 不够，要同时改这个路径（或留空让它按名字去 Hub 找）

#### `RERANK_BATCH_SIZE` = `16`

本地推理时的批大小。显存/内存紧张就调小（8 或 4），不影响结果只影响速度。

#### `HF_ENDPOINT` = `"https://hf-mirror.com"`

HuggingFace 镜像。国内直连 huggingface.co 基本必超时。

- ⚠️ 必须在 `import huggingface_hub` **之前**设进环境变量才有效；
  `predownload_rerank.py` / `rerank.py` 内部已经处理好这个顺序
- 设空串 `""` = 用官方源

#### `RERANK_LOAD_TIMEOUT` = `180`

加载/下载模型最多等多少秒，超时强制降级（daemon 线程实现，进程不会被卡死）。

#### `RERANK_URL` / `RERANK_AUTH` / `RERANK_TIMEOUT`

只在 `RERANK_BACKEND = "http"` 时生效：服务地址、鉴权 token（有的服务随便填）、单次请求超时。

### F. 生成

#### `TEMPERATURE` = `0.0`

采样温度。**评测必须 0**（要可复现），这不是调参项。

- > 0 时同一道题每次答案都不同 → 指标会在噪声里飘
- 谁读它：`run_batch.py`、`page_chat.py`（界面里可以临时调，演示"发散"）

#### `GEN_TIMEOUT` = `600`

界面上「等模型出第一个字」最多等多少秒（超时报错，而不是无限转圈）。

- 本地 8B 在 CPU 上「加载模型 + 预填充 2400 字上下文」可能就要 2~4 分钟，
  之前 180 秒会误判成「生成失败」（实测踩过）；云端模型几秒就出首字，不受影响
- 谁读它：`page_chat.py`

#### `NUM_CTX` = `16384`

Ollama 的上下文窗口大小。

- Ollama 默认只有 **2048**，长上下文会被**静默截断**（答案和判断都被悄悄破坏），必须调大
- 只作用于 **`/api/chat`**（`run_batch.py`、`page_chat.py`、`make_reference.py`）
- 评测评委走 **`/v1` 兼容接口**，实测不会截断到 2048，所以 `run_eval.py` 不读这个值
- 调太大 → 占显存/内存、变慢

#### `DISABLE_THINK` = `True`

关掉 Qwen3 的「思考模式」，实现方式是在 user 消息末尾加官方的 `/no_think`。

- 开着思考 → 输出前先写一大段推理，**慢很多**（实测一句「SWOT 是什么」含思考要 70~155 秒）
- 关掉 → 快，但复杂问题的推理质量可能下降
- ⚠️ 历史坑：旧版这里拼的是一串 `<arg_key:...>`，它**不是** qwen3 的开关，
  模型会把它当正文复述出来（回答里出现「（注：`<arg_key:...>` 为系统生成的唯一标识符…）」）。
  已修正
- 谁读它：`run_batch.py`、`page_chat.py`、`check_pipeline.py`

#### `RAG_SYSTEM_PROMPT` = 严格版提示词

回答系统的 system prompt。当前规定：只用参考资料、没答案就拒答、不改写数字名称、中文简洁。

- 收紧 → `faithfulness` 涨、拒答变多（`answer_relevancy` 可能掉）
- 放宽 → 回答更自然，但幻觉风险上升
- 它是**影响 faithfulness 最大的单一因素**，但改它要重跑生成（40 分钟/组）
- 谁读它：`run_batch.py`、`page_chat.py`

### G. 评测（指标与评委）

#### `METRICS` = `[]`

要跑哪些指标。留空 = 自动：`reference` 填满就跑四个，没填满只跑生成侧两个。
也可手动指定子集，例如 `["faithfulness"]`。

#### `REF_MODEL` = 自动跟随 `JUDGE_MODEL`

起草标准答案（`reference` 列）用的模型。

- 必须 ≠ `GEN_MODEL`，否则等于选手自己出标准答案
- 留空会自动等于 `JUDGE_MODEL`，这样你只改一处
- 谁读它：`make_reference.py`

#### `REF_TOP_K` = `20` ⭐ 决定 `context_recall` 的口径

起草标准答案时，用**多大的 top_k 重新检索**来喂给起草模型。

- 如果直接用评测时的 `TOP_K` 段起草，参考答案每句话必然能在这些段里找到
  → `context_recall` 恒等于 1.0，这个指标彻底失效
- 所以这里要比 `TOP_K` 大得多，让参考答案的信息面更宽
- 调它 = 改 recall 的"分母"，**不改检索本身**；改完要重跑 `make_reference.py` + `run_eval.py`
- 谁读它：`make_reference.py`

#### `REFERENCE_PROMPT` = 起草标准答案的提示词

当前要求「1~3 句话、只用原文措辞、没答案就写"文档未提及"」。

- 要求写得更细 → 参考答案更全面 → `context_recall` 下降（要覆盖的要点变多了）
- 这是指标的**口径参数**，不是系统参数

#### `SIM_THRESHOLD` = `0.45`

`make_reference.py` 用它判断「这题文档里到底有没有答案」：余弦相似度低于它就**不调模型**，
直接标成「文档未提及」。

- 调高 → 更多题被判成"没答案"，reference 里"文档未提及"变多
- 调低 → 更多题会被硬起草，可能逼模型编答案
- ⚠️ **只对余弦相似度有效**，不能拿它卡 rerank 分数（两个量纲不同）。
  为此数据集里同时写了 `top1_similarity`（排序分数）和 `top1_vector_similarity`（余弦），
  门禁一律用后者
- 谁读它：`make_reference.py`、`diagnose_scores.py` / `show_answers.py`（只用于展示告警）

#### `EXCLUDE_NO_ANSWER_FROM_RETRIEVAL` = `True`

「文档未提及」的幻觉探针题，要不要参与 `context_recall / precision`。

- `True`（默认）：从检索指标里剔除。这类题不存在「该召回什么」，硬算必然 0 分，是**假警报**
- 它们仍然参与 `faithfulness` —— 那才是它们存在的意义（测会不会瞎编）
- 谁读它：`run_eval.py`

#### `HIDE_DEPRECATION_WARNINGS` = `True`

屏蔽 ragas 的 DeprecationWarning（它 0.4.x 还在用老 import 路径，屏幕会被刷）。
改 `False` 看完整警告。

#### `EVAL_MAX_RETRIES` / `EVAL_TIMEOUT` / `EVAL_MAX_WORKERS` / `EVAL_RETRY_WAIT` = `4` / `300` / `1` / `60`

打分的容错与并发：

- `EVAL_MAX_RETRIES`：单次打分失败重试几次（实测 1 次时 NaN 率能到 25%）
- `EVAL_TIMEOUT`：单次调用超时秒数，云端模型建议放宽
- `EVAL_MAX_WORKERS`：并发数。**云端模型报 429 时设为 1**；本地 Ollama 也扛不住高并发
- `EVAL_RETRY_WAIT`：429 限流窗口通常 60 秒，提示文案用它
- 谁读它：`run_eval.py`（`experiment.py` 复用它的构造器，所以实验也吃这套）

### H. 版本与自动化

#### `VERSION` = `"v1"`

版本号。它决定输出文件名：`data/eval_data_v1.xlsx`、`data/scores_v1.csv`。
`compare.py` 靠它把多个版本堆成一张对比表。

#### `AUTO_BUMP_VERSION` = `True`

建库时如果**知识库内容真的变了**（内容指纹不同），自动把 `VERSION` +1 并备份 `config.py`。

- 重复建库但内容没变时不会 +1（避免版本号虚胀）
- 想手动控制：`python build_index.py --no-bump`，或把这里设 `False`
- ⚠️ 旧版脚本建的索引没有内容指纹字段，第一次重跑时不会 +1，那次请手动改版本号
- 谁读它：`build_index.py`

### I. 派生值（**不要手改**）

这几个是 `config.py` 根据上面的参数算出来的，手改会在下次导入时被覆盖：

|---|---|---|
| `COLLECTION` | `kb_{EMBED_MODEL}_{CHUNK_SIZE}` | 向量库文件名，换模型/换块大小自动换库 |

| `UI_OVERRIDES_APPLIED` | 实际生效的覆盖项 | 给界面显示「哪些参数被覆盖了」 |

### J. 前端覆盖：`data/ui_overrides.json`

Streamlit「参数与指标」页点「应用参数」时会写这个文件，`config.py` 导入时读它并覆盖同名参数。

- 只接受白名单里的键（`_OVERRIDABLE`），并做类型校验 —— 写坏了也不会让脚本崩溃
- 目的是让**界面上看到的参数**和**命令行跑的参数**一致
- 取消：点界面「↩️ 恢复 config 默认」，或直接删掉这个文件
- ⚠️ 它是**持久的**：下次 `python run_batch.py` 也会用这套值。跑正式实验前先确认

### K. 一个"隐形参数"（不在 config 里，别找错地方）

| 参数 | 在哪 | 说明 |
|---|---|---|
| `STEP_TIMEOUT` / `GEN_TIMEOUT`（体检专用） | `check_pipeline.py` 顶部常量（20 / 120 秒） | 体检脚本每步的超时，**故意**比界面短，好早点暴露问题。调它只影响体检结果，不影响真实问答 |

> 界面用的 `GEN_TIMEOUT` 以前是"隐形参数"（只靠 `getattr` 兜底 180 秒），
> 现在已经在 `config.py` 里显式定义（600 秒），见 F 节。

### L. 症状 → 该动哪个参数

| 症状 | 先看这个 | 再考虑 |
|---|---|---|
| 回答"没提到"但文档里明明有 | `TOP_K` 调大、确认 `RERANK_ENABLED=True` | `RETRIEVE_K` 调大、换 `EMBED_MODEL` |
| 回答里混进大量无关内容 | `TOP_K` 调小、开 rerank | `CHUNK_SIZE` 调小 |
| 该答的题全在拒答 | `RAG_SYSTEM_PROMPT` 放宽 | `SIM_THRESHOLD` 调低、检查检索相似度 |
| 回答里有编造 | `RAG_SYSTEM_PROMPT` 收紧 | 换更大的 `GEN_MODEL` |
| 打分全是 NaN | `EVAL_MAX_RETRIES` 调大 | 换更大的 `JUDGE_MODEL`（要支持 tools） |
| 云端评委报 429 | `EVAL_MAX_WORKERS = 1` | 等 `EVAL_RETRY_WAIT` 秒再跑 |
| 一句问答等好几分钟 | `GEN_MODEL` 换小/换云端 | `RETRIEVE_K` 调小、关 `RERANK_ENABLED` |
| 界面卡在「检索中…」 | `RERANK_LOCAL_PATH` 是否存在 | 先跑 `python predownload_rerank.py` |
| 检索侧指标恒等于 1.0 | `REF_TOP_K` 太小、reference 太粗 | 见 §4 的 P4 |
| 换了嵌入模型后报维度错误 | 正常现象 —— `COLLECTION` 已自动换名 | 重跑 `build_index.py` |

**F 的两条附带发现**（2026-11-05）：

- `faithfulness` 有 1 条（TAM/SAM/SOM）**稳定 NaN**：评委输出被截断（`IncompleteOutputException`），
  重打两次仍是 NaN → 这不是偶发抖动，是评分链路要修的点。
- `answer_relevancy` 的两条 0 分（市场洞察对比、SPAN/FAN/PDC）**重打后仍是 0.000**，是真实缺陷：
  前者回答里写"MM流程未在资料中明确定义"，后者直接拒答。

**v3 上的 4 组对照（G1~G4）一句话**：`TOP_K=5 + rerank 开 + BM25 关` 就是当前最优组合；
把 `TOP_K` 改 3 或 8 都更差，关 rerank 精度掉 0.196，开 BM25 精度掉 0.056。
**注意均值会被 1 道脆弱题绑架**：「市场洞察 BLM/五看/MM 对比」在 G1/G3/G4 里都掉到 0.000。
完整逐题数据见 `实验结果.md`。

**E 的细节（为什么说"看不出收益"）**：8 题里 7 题的逐题分数与 A 完全一致，
只有「我要设计一个系统市场洞察应该有哪些模块」这题 recall `1.0 → 0.0`、precision `0.59 → 0.64`。
那题的相关内容散在 4 份需求文档里，RRF 融合后 BM25 偏好的长段落挤掉了覆盖参考答案要点的那几段。
所以在这套**概念型**题库上，混合检索没有体现出优势。

**但它在关键词型查询上是明确更强的**（同一句「IRR 二分法怎么算」，TOP3）：

| 检索方式 | 结果 |
|---|---|
| 纯向量 | 组合分析（0.499）、组合分析（0.474）、**方法论·模型对比（0.425，无关）** |
| 混合 | 组合分析里讲 IRR/二分法的 3 段（RRF 分最高） |

→ 结论：**代码保持可用、默认关闭**；等题库扩到 20~30 题并加入关键词型问题后再决定是否默认开。

**由此确定的事实：**

- **rerank 有效**：precision `+0.089`（≈3.6× 噪声）、recall `+0.125`（1 题从 0→1）
- **TOP_K 5→3 不值得**：recall −0.125（真漏）、precision +0.024（噪声内）、耗时仅省 8%
- **rerank 的代价是每題 +45 秒**（纯 CPU；8 题 0.6s → 360s）
- **`RETRIEVE_K` 才是 rerank 的成本大头**，降 `TOP_K` 省不了时间
- **混合检索在这套 8 题上没有收益**（precision 噪声内、recall 掉 1 题），但关键词型查询明显更准
- **v3 换语料后 recall 从饱和的 1.000 回到 0.927**：扩语料 + 扩题库才是恢复区分度的正解，不是调参数
- 工程测量：生成 3~5 分钟/题、评测 5 分钟/轮、`run_batch` 10 题约 31 分钟；
  BM25 建索引 ~50ms、查询 ms 级（对比 rerank 的 45s/题可忽略）

### 两个硬约束（决定实验分辨率）

1. 同配置重复跑的差值 = **0.0245**（precision）→ 小于这个量级的差异不能当结论
2. 8 道题时 `context_recall` 的最小刻度是 **0.125**（1/8）→ 想分辨更细的效应，
   必须先把题库扩到 20~30 题

## 4. 还没做：按「性价比」排序

### P0 · 先扩题库（这是所有后续实验的前提，不是可选项）

8 题时 recall 的刻度是 0.125、噪声 0.0245，很多参数的效应被吞掉。
`questions.txt` 加到 20~30 题（覆盖四类：直给答案 / 跨片段整合 / **文档没有答案** / 易混淆），
成本：一次 🐢 完整实验（约 40 分钟）+ 人工过一遍 reference。

> 不做这一步，后面所有「±0.03 的差异是不是真的」都会变成争论。

### P1 · 低成本高信息（⚡ 每项 10 分钟以内）

| 实验 | 怎么设 | 想验证 |
|---|---|---|
| `RETRIEVE_K` | TOP_K=5、rerank 开，20 / 12 / 8 三档 | 能不能质量不掉、把每題 45s 砍成 25s |
| `RERANK_MODEL` | bge-reranker-base（570MB）vs v2-m3 | 小模型够不够用（要 `predownload_rerank.py` 下载） |
| `EXCLUDE_NO_ANSWER_FROM_RETRIEVAL` | True / False | 幻觉探针题对检索指标的污染有多大 |
| `HYBRID_BM25_WEIGHT` | 1.0 / 0.5 / 1.5 | 上一轮 1:1 掉了 1 题召回，降低 BM25 权重能不能既保住关键词优势又不伤召回 |

### P2 · 生成层（🐢 每组 40 分钟）

| 实验 | 怎么设 | 想验证 |
|---|---|---|
| `GEN_MODEL` | qwen3:8b / qwen3:4b / gemma4:31b-cloud | 回答质量 vs 3~5 分钟/题 的取舍 |
| `DISABLE_THINK` | True / False | 思考模式对 faithfulness 和速度的影响 |
| `RAG_SYSTEM_PROMPT` | 严格版 / 放宽版 | 拒答过多 vs 幻觉增加的边界在哪 |

### P3 · 知识层（🏗️ 每组 1.5 小时左右）

| 实验 | 怎么设 | 想验证 |
|---|---|---|
| `CHUNK_SIZE` | 500 / 800 / 1200（overlap 按 15% 同比例） | 当前 800 是不是最优（会换 collection） |
| `EMBED_MODEL` | qwen3-embedding:0.6b / bge-m3 | 中文检索谁更强（会换 collection） |

### P4 · 测量层（不改系统，但改你看到的数字）

| 实验 | 怎么设 | 想验证 |
|---|---|---|
| `REF_TOP_K` | 10 / 20 / 40 | recall 的「分母」有多敏感 —— 这决定 recall 的可信度 |
| `JUDGE_MODEL` | gemma4:31b-cloud / qwen3:8b | 评委换一个，分数差多少（量化「测量噪声」） |
| `REFERENCE_PROMPT` | 1~3 句 / 列举全部要点 | recall 是否只是「参考答案写得多细」的镜像 |

## 5. 实验纪律（前两条已经被验证过）

1. **一次只改一个变量** —— 否则不知道变化是谁造成的。
2. **先 OFAT 扫描，再对有交互的参数做 2×2** —— 已经发现 rerank 与 TOP_K 有交互：
   rerank 在 TOP_K=5 时救回 1 道题的召回，在 TOP_K=3 时完全没救回来。
3. **差值必须大于噪声（0.0245）才下结论**，小于 0.05 一律当噪声。
4. **同配置至少复跑一次**，尤其是「提升很小、刚好跨过阈值」的情况。
