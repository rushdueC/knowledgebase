## 2. 五个结论

### ① `rerank` 是这套系统的命门（G3）

关掉它：precision **0.900 → 0.704（−21.8%，8 倍噪声）**、recall −0.068，而**省下的时间只有 6 分钟**。
两题直接崩：「组织 KPI 分类」1.000 → 0.000（连 recall 都归零）、「华为 DSTE」1.000 → 0.333。

→ **`RERANK_ENABLED` 永远不要关**，除非机器慢到跑不动。

### ② `RETRIEVE_K` 比 `TOP_K` 重要得多（K0 vs G1/G2）

| 改动 | recall Δ | precision Δ |
|---|---|---|
| `RETRIEVE_K` 20→12（K0） | −0.042 | **−0.122** |
| `TOP_K` 5→8（G1） | +0.021 | −0.072 |
| `TOP_K` 5→3（G2） | −0.031 | +0.016 |

候选池砍到 12，rerank 就"没料可挑"了 —— 印证了之前的判断：**rerank 的成本在候选池上，收益也在候选池上**。
想省时间请动 `RERANK_MODEL`（换小模型）或加 GPU，**别动 `RETRIEVE_K`**。

### ③ `chunk=800` 就是最优，而且**严格口径证明了这点**

先看修正前后的差别（本轮最有方法论价值的一组）：

| 组 | 旧口径 precision | 严格口径 precision | 差 |
|---|---|---|---|
| K1 `chunk=500` | 0.7872 | **0.8635** | +0.076 |
| K2 `chunk=1200` | 0.8750 | **0.8576** | −0.017 |

- 旧口径下 K1 的 0.787 有明显偏低成分：**参考答案是按 800 块起草的，跟 500 块的切法没对齐**
- 补齐「用新索引重新起草参考答案」后，K1 从 0.787 升到 0.864 —— 但仍**低于基线的 0.900**
- K2（1200 块）严格口径反而更低（0.858），说明大块把细节吞掉了

→ **`CHUNK_SIZE=800` 处于"覆盖 vs 精度"的最优点，500 和 1200 都不如它。**

### ④ `overlap` 加倍基本没用（K3）

`overlap` 100 → 200 只多切出 85 块（398 → 483），两个指标都在噪声内（−0.016 / −0.006）。
代价是**建库时间 +1.5 倍**，不值。保持 100。

### ⑤ `bge-m3` 是唯一"两个指标都不亏"的改动（K4）

| | 基线（qwen3-embedding:0.6b） | K4（bge-m3） | Δ |
|---|---|---|---|
| recall | 0.9271 | **0.9479** | +0.021 |
| precision | 0.9003 | **0.9097** | +0.009（噪声内） |
| 建库耗时 | 15.8 分钟 | 11.9 分钟 | **更快** |

precision 的 +0.009 在噪声内，但 **recall 的 +0.021 是这 11 组里唯一"不退化"的召回改善**，
而且建库还更快。**建议作为下一轮的候选默认值**（需重建库 + 更新 `COLLECTION`，成本约 12 分钟）。

## 4. 两条工程教训（本轮踩出来的）

### 4.1 `COLLECTION` 名字里没有 `overlap` → 建库会静默覆盖

```python
COLLECTION = f"kb_{_safe(EMBED_MODEL)}_{CHUNK_SIZE}"     # ← 少了 overlap
```

K3（`overlap=200`）建库时写的是同一个 `kb_..._800`，**把基线的 398 块库覆盖成了 483 块**。
之后任何用 baseline 参数跑的结论都会是错的（参数写 100、库是 200）。

- 现象：`config.py` 写 `CHUNK_OVERLAP=100`，但 `vector_store` 里是 483 块
- 修复：重建 800/100（15.8 分钟）
- 建议：把 `overlap` 拼进 collection 名，或建库后在 meta 里校验并报警

### 4.2 `data/ui_overrides.json` 残留会污染整机参数

队列被杀在写 overrides 之后 → 文件留了 `{"EMBED_MODEL": "bge-m3:latest"}`。
**之后每条命令都会用 bge-m3**，包括你以为在跑基线的那些。

- 现象：`config.COLLECTION` 变成 `kb_bge-m3_latest_800`，但你以为在跑 qwen3
- 修复：队列脚本第一步先删 overrides；每阶段结束也删
- 建议：任何脚本写 overrides 都要 `try/finally` 恢复，并在日志里打印"当前生效参数"

## 7. v4 正式基线（bge-m3，完整四指标）

2026-11-06 把默认 embedding 换成 `bge-m3`，用**同题库、同评委、同参数**重跑了一次完整链路
（`run_batch` → `make_reference` → `run_eval`），产出 `eval_data_v4.xlsx` / `scores_v4.csv`。

| 指标 | v3（qwen3-embedding） | **v4（bge-m3）** | Δ | 说明 |
|---|---|---|---|---|
| faithfulness | 0.9667（2 NaN） | **0.9731**（2 NaN） | +0.006 | 两者都是 14/16 有效（同一批评委截断） |
| answer_relevancy | 0.7714 | **0.8237** | **+0.052** | 最大改善 |
| context_recall | 0.9271 | **0.9531** | **+0.026** | 超过噪声 |
| context_precision | 0.9003 | **0.8285** | **−0.072** | 唯一退化，≈3 倍噪声 |

**怎么读这张表**：四个指标里三个变好。但 precision 的退化**不能简单归因于 bge-m3** ——
v4 的参考答案是用新库**重新起草**的（`make_reference`），参考文本变了。
真正干净的 A/B 是 K4（**同一份参考答案**、只换 embedding、只重检索）：

| | recall | precision |
|---|---|---|
| K4（同参考答案） | 0.9479（+0.021） | 0.9097（+0.009，噪声内） |

→ **"只换 embedding"时 bge-m3 略优**；"换 embedding 且重新起草参考答案"时 precision 掉 0.072。
后者说明新参考答案把"该有什么内容"的门槛抬高了，而不是检索变差。

### 差异集中在两道题

| 题目 | precision v3→v4 | recall v3→v4 | relevancy v3→v4 |
|---|---|---|---|
| 做市场洞察要覆盖哪些维度？BLM/五看/MM 异同 | **1.000 → 0.200** | **0.667 → 1.000** | **0.000 → 0.910** |
| 组合分析里 SPAN/FAN/PDC 怎么衔接 | 0.333 → **0.000** | 0.500 → 0.500 | 0.000 → 0.000 |
| 战略地图/平衡计分卡/战略解码的顺序 | 0.950 → 0.833 | 1.000 → 1.000 | 0.966 → 0.917 |
| 其余 13 题 | 不变或微升 | 不变 | 平均基本持平 |

- 第一道题是**这一轮最大的收获**：bge-m3 终于把 MM 流程的内容召回了（recall 0.667 → 1.000），
  回答也从"答非所问（relevancy 0.000）"变成"切题（0.910）"。
  代价是 5 段里塞进了更多只沾边的片段 → precision 掉到 0.200。
- 第二题依旧拒答（两个 embedding 都救不了，属于 §5.6 说的"单查询被最强来源吸走"）。
